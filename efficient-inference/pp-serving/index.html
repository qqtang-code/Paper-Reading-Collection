01 · Overview

速览:这篇论文在赌什么

大多数线上 LLM 服务系统的默认答案是多卡就上张量并行(TP):把每层的权重矩阵切开放到 4 张卡上,一次 all-reduce 把部分和拼回来,每 token 时延低、负载天然均衡。但这个答案有一个隐含前提——卡之间得有 NVLink 那样的高带宽互连。公共云里大量 GPU 服务器、以及 AMD GPU 和各类 NPU,走的是 PCIe;在这类机器上,TP 每层两轮 all-reduce 的通信量会直接把收益吃掉。

流水线并行(PP)的通信量小得多:模型按层深切成若干 stage,激活值只在相邻 stage 之间点对点传一次,microbatch 依次流过各 stage 就形成了流水。但它有两个老问题:一是 pipeline bubble——只要各 stage 的计算量不等,就必然有空转;二是在线服务里"各 stage 计算量相等"这件事根本不成立,因为请求到达时间和输入长度都是抖的。论文的判断是:PP 在带宽受限机器上本来就该赢,它没赢是因为调度没为在线服务改过。于是它把 PP 的失衡拆成三类,再各配一把抓手。

三类失衡(论文的分解)
P-P / P-D / D-DPrefill-Prefill、Prefill-Decode、Decode-Decode。前两类由"长度不等"和"阶段混杂"造成,第三类由"请求数不等"造成。
三把抓手(两机制 + 一调度)
DCPgreedy → DCPpred → +DS动态 chunk 大小(反馈式 / 预测式),再把请求在 microbatch 之间迁移(delay scheduling)。
主结果(AzureConv,Qwen2.5-32B)
TPOT −35% · E2E −31%相对"离线调好静态 chunk"的 PP 基线;真实 trace 上 SLO 达成率 92.5% → 94.6%。
最锋利的一个数
1.4× goodputdecode-heavy 负载上 delay scheduling 的单独增益;同一 trace 上把静态 chunk 从 512 改成 1024,SLO 达成率从 92.5% 掉到 6.9%。

先把结论摆清楚,再逐段拆证据。论文的贡献可以写成三句话:

  • 诊断:在线服务下 PP 的失衡不是一种,而是三种(P-P / P-D / D-D),它们由不同的原因触发,也必须用不同的手段消除——这一点是全文最有解释力的部分。
  • 两个机制:动态 chunked prefill,先用一个反馈控制器(greedy)证明"改 chunk 就能压气泡",再用一个轻量时延预测模型(预测式)解决反馈滞后;
  • 一个调度:delay scheduling,把 decode-only 迭代里的请求在 microbatch 之间挪动,专门对付 greedy/predictive 都碰不到的 D-D 失衡。
一句话记住它:论文没有发明新的并行方式,也没有写新 kernel;它把"PP 在在线服务里为什么慢"翻译成了一个每轮迭代都要重算的 chunk 大小与 microbatch 组成问题,然后用 SLO 作为约束去解它。收益全部来自"少空转",而不是"算得更快"。
02 · Background

背景:TP 与 PP 的成本结构、两个时延指标

2.1 同一个模型,两种切法

张量并行(TP)切的是层内张量:注意力投影、FFN 的大权重矩阵沿某一维切开,每张卡算一部分 GEMM 与 attention,再用 all-reduce 把部分和聚合回来,语义上等价于一个完整层。好处是每张卡都持有全部层,单次前向里所有卡同时在算,单 token 时延低、负载均衡几乎是白送的;代价是每层都要通信,而通信量随隐藏维与 batch 走,必须有高带宽互连才压得住。

流水线并行(PP)切的是层深:连续的若干层组成一个 stage 放在一张卡上,microbatch 依次流过各个 stage;stage 0 在处理第 $i+1$ 个 microbatch 时,stage 1 正在处理第 $i$ 个,靠流水掩盖时延。通信只在相邻 stage 间点对点传一次激活,量级远小于 TP。代价是引入了 bubble:某个 stage 没事干的时候,其它 stage 想快也快不了。

两种并行方式的成本结构对照(据论文 §2.2 整理,非论文原表)
维度张量并行 TP流水线并行 PP
切分维度层内张量(注意力投影、FFN 权重矩阵)层深(连续若干层 = 一个 stage)
通信模式每层 all-reduce(集合通信),每张卡参与整次前向相邻 stage 间点对点传激活,microbatch 顺序流动
通信量级大,需要 NVLink 级别的高带宽才能被隐藏小,PCIe 甚至更弱的互连也能承受
负载均衡天然均衡:每张卡执行同一组算子依赖 batch 组成:各 stage 计算量不等就空转
主要风险通信成为瓶颈;带宽不足时收益被吃光pipeline bubble;调度复杂度高、框架支持不成熟
论文的态度在 NVLink 集群上仍是务实之选在带宽受限机器上应被重新考虑,前提是把气泡压掉

2.2 两个时延指标,一个复合目标

在线服务用两个指标刻画体验:TTFT 衡量 prefill 阶段(用户等第一句话要多久),TPOT 衡量 decode 阶段(吐字速度)。按 MLPerf inference 的口径,论文采用 TTFT SLO = 2,000 ms、TPOT SLO = 200 ms,并把 goodput 定义为"P90 的 TTFT 与 TPOT 同时满足 SLO 时的最高请求率"——注意这是一个单标量:它只关心"能撑到多高的到达率",不关心低负载下时延有多好。这一点在后面点评里会回来。

还有一个绕不开的背景:iteration-level scheduling(ORCA, Yu et al., 2022)让请求可以逐迭代进出批次;chunked prefill(Sarathi-Serve, Agrawal et al., 2024)把长 prompt 切成固定大小的 chunk 分多轮 prefill,避免一次长 prefill 把同批次里正在 decode 的请求顶到 200 ms 以上。这两件事已经是 vLLM、SGLang、TensorRT-LLM、Dynamo 的标配。论文的所有改造都建立在这个"每轮迭代重新组批"的调度模型之上。

2.3 论文的起点:4 张 A100(PCIe)上的 TP vs PP

作者先用最朴素的方式把问题摊开:同一台 4×A100 40GB(PCIe 4.0)的机器、同一个 Qwen2.5-32B、同一份 Azure Conversation 流量,分别用 TP 和 PP(带 chunked prefill)去跑,扫描请求率,看 TTFT 与 TPOT 的 P90。

这张图还顺手解释了后文所有优化的方向。TP 的 TTFT 在高请求率下陡峭上升,是排队(queueing)带来的;PP 的 TPOT 陡峭上升,是空转带来的。两条曲线的形状不同,说明瓶颈不同:想赢 PP 这一侧,不需要让每一轮算得更快,只需要让 4 个 stage 少等彼此。这也是为什么全文的抓手都是"调度"而不是"算子"。

本节小结:PP 在带宽受限机器上的优势是结构性的(通信少、TTFT 低),劣势也是结构性的(依 batch 组成而变的气泡)。所以问题不是"PP 行不行",而是"气泡能不能被调度吃掉"。
03 · Observation

观察:气泡的三种形状与三张性能剖面

3.1 气泡不是一种,是三种

论文的第一个贡献是给 pipeline bubble 做了一次"分型"。它假设一个两 stage、每 microbatch 最多 3 个请求的小例子(便于画图),把任一时刻的批次组成归纳成三种失衡:

这个分类的价值在于它把"气泡"从一个笼统的性能现象,变成了三个可以分别对账的原因:P-P 来自长度方差,P-D 来自阶段混杂,D-D 来自请求数方差。后文的三把抓手与这三类一一对应(见 3.3 末的对照表)。也可以顺带看出,Tensor Parallelism 为什么天生没有这个问题:它根本不把输入批次拆成 microbatch,而是把同一批的计算均摊到所有卡上——所以 TP 的均衡是"结构上白送"的。

3.2 为什么会失衡:三张性能剖面

光有分类还不够,得证明"失衡的量级足以致命"。论文给出三张 microbenchmark(Qwen2.5-32B、单张 A100):

把这三张图的结论拼起来,就是论文的因果链:输入长度决定 prefill 开销、请求数决定 decode 开销,而在线流量的到达时间和长度都在抖,所以每轮迭代凑出来的 microbatch 组成天然不等;一旦 4 个 stage 的计算量不等,bubble 就出现;而 (c) 的台阶又说明,靠"多凑一点"来填平差距本身是有阈值效应的——129 个 token 和 256 个 token 几乎一样贵,所以稍微越过边界的批次是"白付费"。

3.3 旋钮只有一个:chunk 大小

既然 P-P 与 P-D 都源于"一个 microbatch 里的 prefill 太长",最直接的干预就是 chunked prefill:把长 prompt 切成固定大小的小块,prefill 的计算量就被人为压平了。但 chunk 大小是个双向的旋钮。

所以"该用多大 chunk"没有全局答案:低负载时要小(压气泡),高负载时要大(保吞吐),而这个"最优点"随负载、模型、甚至 workload 的输入分布漂移。论文的实验也印证了这一点——32B 在 AzureConv / CNN / ShareGPT 上最优点在 chunk 512,在 decode-heavy 的 CNN-Reversed 上变成 256;14B 在 AzureConv 上又变成 1024。静态配置注定只在某一个负载点最优。

三类失衡 × 触发条件 × 论文的对应手段(据论文 §3–§4 整理,非论文原表)
失衡类型触发条件典型症状论文的抓手
P-P(Prefill-Prefill)同一轮里 microbatch 的输入长度差很大(如 2048 vs 128)长 prefill 占满一侧,短的早早做完干等;单个气泡可达约 627 ms动态 chunk(把长 prefill 切碎,压平各 stage 的计算量)
P-D(Prefill-Decode)一个 microbatch 全是 decode,另一个全/多是 prefill两侧计算量量级不同,decode 侧空转,TPOT 上升动态 chunk + 预测式"上下界"选 chunk,避免把大 prefill 塞进正在 decode 的轮次
D-D(Decode-Decode)整轮都是 decode,但某个 microbatch 请求数明显更多(如 129 vs 128)线性层台阶导致"多几个请求就多 31% 时间",跨迭代反复空转delay scheduling(在 microbatch 间迁移请求,并对齐 128 的硬件边界)
本节小结:论文把"PP 慢"拆成了 长度方差(P-P)、阶段混杂(P-D)、请求数方差(D-D) 三个可归因的病。前两个病有同一个旋钮(chunk 大小),第三个病必须动批次的组成。这是全文后续所有设计的出发点。
04 · Method

方法:动态 chunk(greedy / 预测式)与 delay scheduling

4.1 目标函数:在两条 SLO 约束下,选"最小的可行 chunk"

论文把 chunk 选择写成一个约束优化:在满足 TPOT SLO 的前提下,选能装下当前负载的最小 chunk。理由很直接——chunk 越小,prefill 被切得越碎,stage 间越均衡、气泡越少;但太小会让 GPU 利用率不足、排队变长、TTFT 变差。所以"最小可行"正是"刚好能把当前负载消化掉"的那个点。

这里有一个很关键、但容易被跳过的设计:两条 SLO 在算法里承担的角色是不一样的。TPOT SLO 是硬约束(chunk 不能再大,否则正在跑的请求会被拖过 200 ms),而 TTFT SLO 被当成负载指示器——等待队列变长说明到达率高,于是放大 chunk 把队列抽干;TTFT 余量充足说明负载轻,于是缩小 chunk 去压气泡。这一点在预测式版本里被推到了极致(见 4.1.2 的下界)。

4.1.1 Greedy:一个只用上下阈值的反馈回路

这个控制器的优点是改动量极小——它只在既有调度器上加了"每 $D_p$ 轮读一次指标、按阈值加减 $\delta$"三行逻辑,不需要模型、不需要预训练,工程上几乎可以立刻落地。论文也坦白它的两个结构性缺陷:

  • 滞后:一次调整要等 $D_p$ 轮才见效,而负载在秒级波动,于是控制器一直在追一个移动目标,长时间停留在次优状态;
  • 观测被污染:它读到的 $\mathrm{TTFT}_{slack}$ / $\mathrm{TPOT}_{slack}$ 是被流水线深度延迟、而且被其它 stage 的 chunk 大小搅过的量,反推不出"当前这个 chunk 到底合不合适"。

4.1.2 预测式:把迭代时延拆成"离线线性项 + 在线注意力项"

为了绕开"反馈滞后",预测式版本直接对每个候选 chunk 预估一次迭代的时延与吞吐。模型拆成两部分:

$$T_{iter} = T_{offline} + T_{online},\qquad T_{offline} = \alpha_0\cdot N_{tokens} + \alpha_1$$

$T_{offline}$ 只依赖这一轮批内总 token 数 $N_{tokens}$,而 $N_{tokens}$ 在 chunked prefill 下几乎由 chunk 大小决定,所以这一项可以用离线 profiling 拟合(论文在 128–2048 的离散 token 数上测一遍)。真正动态的是注意力那部分:

$$T_{online} = \beta_0\sum (L_{past}\cdot L_{pre}) + \beta_1\sum (L_{pre}^{2}) + \beta_2\sum L_{dec} + \varepsilon$$

三项分别对应"当前 chunk 对历史上下文的注意力"($L_{past}\cdot L_{pre}$)、"chunk 自注意力"($L_{pre}^2$)与"decode 请求的注意力"($L_{dec}$),$\varepsilon$ 吸收未建模的运行时噪声。系数 $\beta_0,\beta_1,\beta_2$ 不是离线学出来的,而是在线用递归最小二乘(RLS)更新——每轮拿实测迭代时延与预测值的残差校正一次。论文给了两条"为什么是 RLS"的理由:它用内部协方差矩阵吸收各特征之间的量纲差异($L_{past}^2$ 与 $L_{dec}$ 的量级差得很远,标准梯度下降会被尺度带偏),并且带遗忘因子,能让模型快速跟上 prefill-decode 相互干扰这类非平稳变化。

这里有一个值得单独记住的设计:TTFT SLO 并没有被直接当成"时延上限"去约束,而是被换算成一个最低吞吐下界(到达率匹配吞吐 + 待服务请求的紧迫度)。这一步把"队列时延"这种与当前批次耦合很紧的指标,转成了"这一轮需要吃下多少 token"这种可以直接和 chunk 大小对照的量——这也是它比 greedy 的阈值法更稳的原因。

图 6 右侧那张示例候选表还顺手说明了权衡的形状:chunk 从 128 到 2048,预测时延从 45 涨到 467(约 10.4×),而预测吞吐只从 7127 涨到 14745(约 2.07×)。时延涨得比吞吐快一个量级,所以"能小就小"在多数负载下是对的,只有当吞吐下界被顶到 10k tok/s 以上时才有必要往大 chunk 走(推算:按该表的单调关系,目标吞吐约 7k 对应 chunk 128,约 10k 对应 chunk 512)。

4.2 Delay scheduling:把请求在 microbatch 之间搬一次

chunk 只能调 prefill 的粒度。当整轮迭代里一个 prefill 都没有(decode-heavy)时,DCP 无从下手——此时决定各 stage 计算量的只有"每个 microbatch 里装了几个请求"。而现有系统一旦把请求分进某个 microbatch,它在整个生命周期里就固定在那里(vLLM、SGLang 都是如此),于是失衡会跨迭代反复出现。

具体策略有三条,都是工程上很"轻"的决定:

  • 对齐硬件台阶:平衡 microbatch 大小时,把批大小对齐到 128 / 256 / 384 这类"划算"的边界。依据正是图 3(c)——129 个 token 和 256 个几乎一样贵,所以多出来的那几个请求是纯亏,不如挪走。
  • 阈值式抢占:若某 microbatch 的请求数超出最近的边界但溢出量在阈值内,就临时抢占溢出的部分,把批压回边界;若溢出量超过阈值,则改为把该 microbatch 对齐到"全部 microbatch 的平均请求数",并顺带恢复之前挂起的请求来填空。
  • 按 TPOT 余量选受害者:TPOT 余量不足时,优先抢占较老的请求(它们已经跑了一会儿,更能容忍额外时延),以保护新请求的 TPOT;TPOT 余量充足时,风险变成 KV 耗尽与 TTFT 违约,此时改为抢占较新的请求,让老请求早点跑完、早点释放 KV。
本节小结:论文把 PP 的气泡治理拆成两层——粒度层用动态 chunk 把 prefill 切平(greedy 验证可行性、预测式补上滞后),组成层用 delay scheduling 把 decode-only 迭代的请求重新摊平。两层的输入都是 SLO 余量与 KV 余量,输出都是"下一轮怎么组批"。
05 · Implementation

实现:把论文配置落到一次调度决策上

论文没有单开"系统实现"一章,实现信息散在 §4 的伪码与 §5.1 的环境里。这里把它整理成一张参数清单,并推演一次真实的调度决策,方便判断复现门槛在哪。

实现底座是 SGLang 0.4.1(PyTorch 2.5.1、CUDA 12.4、FlashInfer),硬件是单机 4×A100 40GB(PCIe 4.0)+ 128 核 AMD EPYC 9754 + 768 GB 内存,模型是 Qwen2.5 32B / 14B 的 BF16 版本。三套技术都实现在 SGLang 的调度器里:动态 chunk 改的是"这一轮 prefill 允许多少 token",delay scheduling 改的是"这一轮 microbatch 怎么装、要不要挂起/恢复某些请求"。两者的决策点都在每一次调度迭代,输入都是 SLO 余量与 KV 余量。

把配置落到具体决策上,可以算出两个有意思的结论(以下均为推算,依据论文给定的规则与量级):

  • 反馈延迟相对 SLO 是小的。若按 4 卡纯 PP 推断 $D_p=4$(论文只给了 GPU 数,没给 stage 数),一次 chunk 变更要 4 轮迭代才生效。按文中迭代时延的 P90 量级(约 20–50 ms)估算,一个调整周期约 80–200 ms,远小于 2,000 ms 的 TTFT 预算——所以 greedy 的滞后在"稳态"下并不致命。
  • 但它在"突发"下会掉队。greedy 每次只走一档 $\delta=128$,从最小候选 128 爬到 2048 需要 15 次调整、即 $15\times 4=60$ 轮迭代(约 1.2–3 s)。真实 trace 的高负载是短突发而不是持续高负载,所以这个爬升速度刚好卡在"还没爬到就退了"的区间——这正解释了论文在真实 trace 实验里的观察:greedy 的 SLO 达成率(93.5%)低于预测式(94.5%),差距来自"追不上突发"。预测式因为能直接对候选做一次预测,不需要逐档爬,所以没有这个限制。

还有一处值得强调的实现细节:greedy 的内存分支优先级最高。当 $\mathrm{KV}_{free} < \theta_{mem}$ 时,它不再看时延余量,而是直接把 chunk 压到"刚好大于在跑请求数"的最小候选。这在语义上很清楚——KV 快满时,继续用大 chunk 只会让某些 stage 的 KV 分配失败,不如立刻收小、把在途请求排空、把显存腾出来。这条规则也解释了为什么 DCP 在高负载下反而不会 OOM:它不是靠更大的 batch 提高吞吐,而是靠"别把显存赌在一轮上"。

本节小结:论文的机制本身很轻(一个阈值控制器、一个 RLS 校正的线性模型、一套抢占规则),落地在 SGLang 调度器里;但它把所有需要调的超参都留成了符号($\alpha,\beta,\gamma,\theta_{mem},D_p$,以及抢占阈值与遗忘因子),没有给数值——这是复现与工程移植时最大的不确定项。

07 · Positioning

定位:它站在哪条谱系上

论文在 §6 把相关工作整理成三条线,而它自己正好卡在三条线的交叉点上。

7.1 调度线:从"逐迭代组批"到"逐迭代改 chunk"

ORCA(Yu et al., 2022)提出了 iteration-level scheduling 与 selective batching,让请求可以按迭代进出批次;Sarathi-Serve(Agrawal et al., 2024)在它之上加了 chunked prefill,把长 prompt 切块以保护同批 decode 请求的 TPOT——这两件事现在已经是 vLLM、SGLang、TensorRT-LLM、Dynamo 的默认行为。本文的增量是:把 chunk 大小从"部署时固定的常量"变成"每轮按 SLO 余量求解的变量",并且第一次把流水线结构(端到端时延 ≈ 迭代时延 × $D_p$)显式写进这个求解过程。

7.2 并行线:训练期的 PP 经验不能直接搬

PP 在训练侧有成熟的方法论:GPipe(Huang et al., 2019)的 micro-batch 流水与 PipeDream(Narayanan et al., 2019)的 1F1B 调度,目标都是在固定、可预测的输入上把流水填满。在线服务的输入是随机到达、长度分布随时间变的,训练期那套"把 batch 切成等大的 microbatch"的前提不再成立——本文三类失衡里有两类(P-P、P-D)正是因为这个前提失效。TP 侧则是 Megatron-LM(Shoeybi et al., 2020)的经典做法,论文承认它在 NVLink 集群上仍是务实选择。

7.3 部署线:为什么不走 P-D 分离

另一条主流路线是 phases disaggregation:Splitwise(Patel et al., 2024)、DistServe(Zhong et al., 2024)、Mooncake(Qin et al., 2024)把 prefill 与 decode 放到不同 GPU 上,从物理上消除 P-D 干扰。论文明确不走这条路,理由是那套方案要付出模型权重的重复放置与KV cache 跨机传输的代价,而这些代价在 PCIe 甚至无高速互连的场景里更加不可接受。它选择的是"统一服务 + chunked prefill"的路线,并声称在同等硬件上把气泡压到可接受水平——**注意这里缺一件事:论文没有在同一台机器上跟分离式方案做过端到端对比**(见点评)。

7.4 与前作 Niyama 的差别

动态 chunk 并非全新想法:Niyama(Goel et al., 2025)已经做过"SLO 感知的动态分块"。论文对它的定位很具体——Niyama 优先保证 SLO 合规,但忽略了流水线并行的结构约束,因此气泡问题原封不动;本文则把"迭代预测 × 流水线深度"折成端到端时延,再据此设上下界。这句话也可以反过来读:本文的预测模型之所以值得存在,正是因为它多了一个 $D_p$ 因子——如果没有流水线,预测迭代时延本身就够了。

08 · Assessment

点评:强在哪、能质疑什么、还有什么没披露

8.1 站得住的地方

  • 问题选得准。「TP 是唯一解」这个默认假设确实建立在 NVLink 之上,而公共云的 PCIe 机型、AMD GPU、各类 NPU 都是反例。把 PP 重新推上台面,不需要新硬件,只需要把调度补上——这是一个投入产出比很高的方向。
  • 诊断比方法更有价值。把气泡分成 P-P / P-D / D-D 三类,并各自对应到"长度方差 / 阶段混杂 / 请求数方差",是目前对 PP 服务性能最清晰的一次归因。后来的系统哪怕不用它的算法,也会用它的分类去定位问题。
  • 基线选得诚实。PP 基线不是"随手一个大 chunk",而是每个 workload 离线搜出来的最优值(近乎 oracle);在这种不利条件下仍然胜出,说服力比打一个弱基线强得多。
  • 把 TTFT SLO 换算成吞吐下界是一个可复用的建模技巧:它把与批次强耦合的队列时延,变成了一个能与 chunk 大小直接比较的量。
  • 证据链完整。goodput → 迭代时延 CDF → SLO 收紧 → 合成负载分离病灶 → 真实 trace,每一层都在回答"上一层的数字为什么可信"。

8.2 可以质疑的地方

  • 两侧基线的调优强度不对称。PP 用的是 per-workload 最优静态 chunk,TP 用的却是默认 2,048——而同一篇论文自己就证明了"chunk 选错能让 goodput 掉一半以上"。如果把 TP 也调到最优,两者的差距会缩小多少?论文没有回答,这是本文最应该补的一个对照。
  • 只有一个硬件形态。动机里点名 PCIe、AMD GPU 与 NPU,但实验只有一种 PCIe 机型(4×A100 40GB),没有 NVLink 对照组,也没有 AMD/NPU 实测。因此"PP 在带宽受限机器上更好"这个结论目前只在一种机器上被验证。
  • goodput 是单标量,容易掩盖代价。论文自己也承认 DCP 会略抬 TTFT(Fig 11 里 CNN 的 50 分位以下 DCP 甚至不如 PPstatic)、DS 会让 P99 TPOT 差 15%。这些代价被"goodput 不掉"概括掉了,但对某些业务(对话首字时延敏感)可能就是不可接受的。
  • 预测模型的精度论证偏弱。ALP 的 MAPE(3.26%)不如两层 DNN(2.56%),论文用"预测耗时低 16×、体积小 887×、无需预训练"来辩护。这个辩护合理,但缺少一个关键消融:把 DNN 换进同一个调度器,端到端 goodput 会差多少?没有这个数,"精度够用"就只是推断。
  • 没有和 P-D 分离方案同台。相关工作里花了一整段论证"分离式有额外开销",但唯一的证据是引用,不是测量。在 4 卡这种小规模上,分离式的开销可能确实高,可是读过的人会想要那张对比图。
  • 规模与模型族单一。两个模型来自同一族(Qwen2.5 14B/32B)、固定 4 卡、单一 PCIe 拓扑。$D_p$ 更大(8/16 stage)时,一次 chunk 变更的生效延迟线性增长,预测式的"提前一轮预测"是否还够,论文没有讨论。

8.4 未披露、值得补测的点

  • 全部关键超参的数值。$\alpha$、$\beta$、$\gamma$、$\theta_{mem}$、$D_p$、抢占溢出阈值、RLS 遗忘因子都只有符号范围,没有取值与敏感性分析——复现的人必须自己扫一遍。论文也没有说明这些值是否对 workload 敏感。
  • "最优 TP"对照。未见论文披露把 TP 的 chunk 与 batch 上限一并调优后的 goodput。这是判断"PP 赢多少"的关键控制变量。
  • 跨硬件与跨拓扑。未见 NVLink 机型、AMD GPU、NPU 的实测,也未见 8 卡及以上($D_p \ge 8$)的结果;动机与实验之间存在空档。
  • 与分离式方案的实测对比。未见在同一台机器上与 Splitwise / DistServe 类系统的端到端数字;这一点在相关工作里只做了机理论述。
  • DS 的代价分布。真实 trace 上未见被挂起请求的 TPOT 分布(论文只在合成负载里给出 P99 TPOT +15%),也未给出抢占在极端负载下的抖动。
  • 可获取性。论文未给出代码/artifact 链接;"实现在 SGLang 0.4.1 之上"是否以下游 patch 形式公开,未见披露。

8.5 我的判断

这是一篇"把系统做对"而非"发明新机制"的论文——它的每一块零件(TTFT/TPOT 作为 SLO、chunked prefill、RLS、抢占)都是既有的,新意在于把在线服务的负载动力学真正接到流水线的结构约束上。对读者最有迁移价值的两个技巧是:

  • 把"时延 SLO"翻译成"吞吐下界"——凡是"队列长度会自发调节"的系统,这条换算都能用;
  • 把批大小对齐硬件的台阶(128 / 256 / 384)——这是个不需要任何模型、只要知道 GEMM tile 粒度就能拿到的免费收益。

适用边界也要说清楚:这套东西在 NVLink 集群上收益有限(TP 本来就省心),在超大规模跨机部署上也不是主角(那是 P-D 分离的战场),它真正的战场是单机多卡、互连普通、模型还能整段切开的那些机器——而这恰好是云上最常见、也最常被"默认上 TP"糊弄过去的那一类。
