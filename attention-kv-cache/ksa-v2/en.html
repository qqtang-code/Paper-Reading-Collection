Overview: KSA V2 in one sentence

The whole report argues one thing: in hybrid architectures built around Summary tokens such as KSA, those Summary tokens are wasted — they are computed at every layer and refined layer by layer, yet they are only ever read as a "low-resolution memory" by the KSA layers. The authors observe that the same Summaries can do two jobs at once: act as KV memory that can be compressed further, and act as the index for sparse routing. Two drop-in layer types follow from that idea, together called KSA V2.

One-line mnemonic: C-KSA is about saving memory (compressing the remote Summary KV by a further factor of $k_m$, but only the copy that gets stored, never coarsening the Summary representation that flows between layers); S-KSA is about saving compute (replacing the Full layers that used to read all history with "first let the Summaries pick blocks, then read only the selected original text blocks"). Neither adds input tokens or changes the token layout, which is exactly why both can be retrofitted into an already-trained model.

Section 2Background: where long-context serving actually gets expensive

To see why KSA V2 looks the way it does, split "expensive" into three distinct kinds of expensive. Each has a different best answer, and lumping them together leads to the wrong conclusion.

  • Expensive to store (KV cache grows linearly with the sequence). In standard full attention every token must keep one key and one value in the cache. Double the sequence and you double the memory. This line is linear, and it is the first wall long-context serving hits — batch concurrency is set directly by the per-sequence cache footprint.
  • Expensive to compute (prefill is quadratic). During prefill every query attends to every earlier key, so the work is $O(N^2)$. At 128K this term outweighs the weight matrix multiplications and dominates prefill time.
  • Expensive to read (decode reads all history for every query). Every generated token reads the entire history's KV back out of memory. This is a bandwidth bottleneck rather than a compute bottleneck, and it penalizes latency and throughput at the same time.

The four technical routes the field has taken are, at bottom, trade-offs between these three bills rather than solutions to a single problem:

  1. Per-token compression (GQA (Ainslie et al., 2023), MLA (DeepSeek-AI et al., 2024), and quantization methods such as KIVI) — makes storage per position cheaper while leaving the number of positions unchanged. It compresses "how many bytes per token", not $N$. The payoff on this line is clean and lossless, but the ceiling is explicit.
  2. Sparse attention (DSA (DeepSeek-AI et al., 2025), MoBA (Lu et al., 2025), NSA (Yuan et al., 2025)) — keeps token-level KV and only reduces which positions each query reads. It brings compute and bandwidth down, but the cache itself does not shrink, and it needs an extra criterion for "where should I read".
  3. Sliding window / linear and recurrent attention (sliding window in Mistral (Jiang et al., 2023); recurrent variants in Gated DeltaNet (Yang et al., 2025)) — both storage and compute come down, and the recurrent state is even independent of context length. The price is that direct access to distant original tokens is lost: history can only be read back indirectly through a repeatedly aggregated state.
  4. Hybrid architectures — interleave the above classes by layer, keeping a few full attention layers for direct access to the original text. This is the most robust engineering compromise, and it is where the KSA family sits.
Why hybrid is the main line rather than pure linear.The failure mode of purely linear/recurrent models is not "slightly worse average metrics" but a sudden collapse on tasks that require retrieving an exact distant literal span — an aggregated state is an irreversible summary. Hybrid uses a few full layers as a safety net, downgrading that failure mode from "collapse" to "somewhat more expensive". But it leaves a structural hazard behind: those few full attention layers become the performance and cost bottleneck of the entire model. KSA V2 is aimed squarely at that hazard.

Section 3The upstream KSA recap: how Summary tokens work

Kwai Summary Attention (KSA, (Chu et al., 2026)) is a rather unusual instance of the hybrid route. Its core mechanism fits in one sentence: after every $k_s$ text tokens, insert one learnable Summary token.

Inside a KSA layer, the visible set of a text query splits in two: nearby chunks are read at full resolution (nearby detail matters and is cheap), while distant chunks are read only through their Summary (one KV entry per chunk). That compresses the number of KV entries for distant history from $k_s$ down to 1 — a $k_s$-fold compression along the sequence dimension.

Hybrid KSA interleaves these KSA layers with full attention layers at a 3:1 ratio: three KSA layers followed by one full layer. The left half of Figure 2 in the paper shows exactly this structure.

The most important and most easily missed point: the Summary's KV flows between layers. A Summary token is not an auxiliary entry used only as a cache inside its own layer; its hidden state is passed on as input to the next layer, which reads it and refines it further. The deeper the layer, the more "mature" the information the Summary carries.
This is the key to every design decision in KSA V2: because the Summary must be passed forward, any coarsening of it pollutes every subsequent layer. Conversely, if you want distant history stored more cheaply without polluting later layers, the only way out is "compress on the way into storage, do not compress on the way forward". C-KSA is that sentence translated into an architecture.

The payoff from KSA is real: the paper reports that it outperforms same-sized full attention models on long-range information retrieval. But it also leaves two spaces unexploited — and those two spaces are the entire motivation for KSA V2.

Section 4Two bottlenecks: Summary tokens are under-used

The paper's motivation statement is explicit and can be compressed into one line: a Summary is computed and refined at every layer, yet only ever used as low-resolution memory — losing on both ends.

Bottleneck (i): the compression rate is tied to the chunk

A KSA layer "stores one entry per distant chunk", so compressing harder means only one thing: raising $k_s$. But $k_s$ also determines the granularity of the Summary: the larger $k_s$ is, the more original text each Summary must summarize, so it is a coarser summary; and that coarser Summary is then read and refined by every later layer. In other words, raising $k_s$ is a global coarsening of the representation, and the whole network pays for it.

This is not a theoretical worry. KSA reports its own 4B ablation showing that coarser Summary chunks degrade retrieval performance (the paper restates this conclusion in Related Work, and KSA V2 Section 3.7 runs a dedicated direct-versus-hierarchical compression comparison).

In engineering terms: inside KSA, "save memory" and "keep retrieval accuracy" are two ends of the same knob, and you cannot have only the first. To reach 1024× compression you must move $k_s$ from 8 to 1024, which means each Summary summarizes 1024 tokens — no longer a summary but a flattened average. What KSA V2 does is pull apart two things that used to be welded together: how much you store, and how coarse what you pass forward is.

Bottleneck (ii): the full layer reads all the KV yet pays quadratic prefill

The other half of the waste sits in the full attention layers. Interspersing them among KSA layers does preserve exact access to the original text, but it costs: $O(N^2)$ attention compute during prefill, and reading the whole history for every query during decode. Meanwhile the Summary tokens demonstrably "describe every chunk", and the full layer never consults them at all.

The problem is that most of what the full layer reads in is irrelevant. The measurement the paper offers (an oracle block-selection experiment on a frozen Hybrid KSA, corresponding to Figure 12 and Table 10):

At 128K context, oracle block selection restricts the main attention's read set to about 3.9% of the text positions, yet retains about 82% of the decode attention mass and achieves retrieval performance close to dense.

That statement carries two implications, and both are worth pausing on:

  1. Attention is highly concentrated. Roughly 97% of positions contribute less than 20% of the attention mass. Dense attention spends $O(N^2)$ compute on positions that do not matter.
  2. What is missing is not sparsity but a cheap criterion for "where to look". The oracle is called an oracle because it uses dense attention probabilities to choose. A real system does not have those probabilities, so it needs a router that is cheap enough and learnable during training. And the Summary — which already describes every chunk — is precisely a ready-made router, except that KSA never consults it.

Section 5The core insight: one Summary, two roles

Put the two bottlenecks of Section 4 side by side and the answer is almost self-evident. The paper's insight can be written as one asymmetric statement:

As memory, a Summary can be compressed once more at the moment it is stored, without coarsening the representation that is passed on; as an index, a Summary can direct the exact-access layers to which original blocks to look at. The efficient layers store coarsely, the exact layers read finely, and the Summary connects the two.

Note the most delicate part of that sentence — it avoids coarsening by choosing when to compress rather than how hard:

  • Compress when storing (C-KSA): pool every $k_m$ consecutive Summary KV entries into one Meta KV entry, used to read distant history only inside this layer. The Meta entry is not passed forward. So distant history gains another $k_m$-fold storage compression (a combined $k_s k_m$), while the granularity of the Summary sequence flowing between layers is completely unchanged — later layers still receive Summaries refined at $k_s = 8$ granularity. This dissolves bottleneck (i): the compression rate is decoupled from the representation granularity.
  • Use it as an index when reading (S-KSA): use the existing Summaries to pool the original-text KV of each $b$-token block into block-level routing keys, then use the Lightning Indexer (DeepSeek-AI et al., 2025) to select top blocks, and let the main attention read only the original KV of those blocks. This dissolves bottleneck (ii): the full layer is replaced, prefill is no longer quadratic, and the number of routing candidates is $b$ times smaller than with a token-level index.

There is also one property that matters enormously in practice: neither layer type adds tokens or rearranges the Summary layout. Both consume Summaries that already exist, so they can be retrofitted directly into a pre-trained hybrid model — no tokenizer change, no pre-training from scratch. Every experiment in the paper follows that route, which is also why its experimental cost stays at the "continued pretraining" scale.

Difference from neighbouring work (citation attribution follows the paper's own labelling). CSA in DeepSeek-V4 (DeepSeek-AI et al., 2026) also performs learned dimension-wise aggregation, but it aggregates the KV of text tokens and lets the result participate in subsequent computation as a new entry; C-KSA aggregates the KV of Summaries, and its product is private to the layer. S-KSA differs from DSA in that DSA selects at token level whereas S-KSA drops to block level, with $b$ times fewer routing candidates; and differs from CSA in that CSA's main attention reads compressed text, while S-KSA's main attention reads the original text KV.

Section 7Three contributions and how to read the rest

The paper states three contributions, each matching a problem it solves:

  1. C-KSA: at storage time, compress Summary KV into layer-local Meta entries, so that further compression of distant history no longer requires coarser Summaries.
  2. S-KSA: turn the existing Summaries into block-level routing keys and run sparse attention over the selected original-text blocks.
  3. Deployment and boundaries: a retrofit recipe and GPU kernels that convert a pre-trained Hybrid KSA, with RULER performance level with the parent model; plus an explicit report of where the remaining cost sits and under what conditions the method fails.

The third deserves a separate sentence. This report is candid about failure modes: the remaining cost is mainly the original-text KV kept by the sparse layers, and block selection degrades on aggregation-heavy tasks (frequent-word extraction falls from 45.00% to 26.67%). A technical report willing to spell out its degradation is worth more to an engineer than two extra points of headline metric.

Section 8Notation and overall layout: count your cards first

The method section pins down its symbols immediately. Every formula that follows uses them, so two minutes spent here pays for itself many times over.

  • $T_i$ — a text token. The thing the model is actually trained to predict.
  • $S_c$ — a chunk Summary. The summary token of the $c$-th chunk, inserted once every $k_s$ text tokens.
  • $M_g$ — a Meta KV entry. The compressed product of the $g$-th group of Summaries, used only in its own layer.
  • $k_s$ — the chunk size, i.e. how many text tokens one Summary covers. Both 1.9B and 4B use 8.
  • $k_m$ — how many consecutive Summaries are compressed into one Meta entry. 128 for 1.9B, 32 for 4B.
  • $b$ — how many text tokens one routing block contains. Set to 4, and $b$ is required to divide $k_s$.
  • $W$ — how many complete chunks the local window covers. KSA/C-KSA use a "sliding chunk number" of 128, which with $k_s=8$ gives a local window of 1024 text tokens.
  • $K$ — the remote budget, measured in original text tokens, 4096 for both 1.9B and 4B. Note that it counts tokens, not blocks: the number of selectable blocks is $K/b$.
  • $q_t$, $O_t$ — the attention query and output at position $t$.

The overall layout follows Hybrid KSA's 3:1: three C-KSA layers followed by one S-KSA layer, repeating. This matters — KSA V2 does not change the layer ratio, it only replaces each layer of the old "three KSA + one Full" pattern with a stronger version. The conversion is therefore drop-in: layer count, width, Summary layout and tokenizer are all untouched.

Why does the 3:1 ratio not need changing?Because the two new layer types address two orthogonal wastes inside the hybrid structure: C-KSA makes the memory-saving layers cheaper still, and S-KSA makes the exact-access layer cheaper. The 3:1 ratio itself encodes an empirical question — "how thick does the accuracy safety net need to be" — and KSA V2 has no evidence to move it, so it does not. That is engineering restraint in the right place.

Section 9C-KSA part one: two-level aggregation, Equations (1)–(4)

What C-KSA does fits in one sentence: KSA already inserted Summaries into the text sequence; C-KSA aggregates the Summary sequence once more. It pools every $k_m$ consecutive Summary KV entries into a single Meta KV entry, so the compression factor for distant history goes from $k_s$ to $k_s k_m$, while nearby text stays directly readable.

There are two levels of aggregation here, pointing in completely different directions — do not mix them up:

Level one: Text → Summary (pre-existing in KSA)

Cut the text sequence into chunks of $k_s$ tokens and append one Summary token $S_c$ at the end of each chunk. All Summaries share the same learnable initial embedding and use exactly the same attention and FFN parameters as text tokens — a Summary is not a special side module, it is simply another kind of token in the sequence.

At each layer, $S_c$ attends to the text tokens inside its own chunk plus itself, aggregating chunk-level information from them. There is one positional detail: text tokens keep their original position indices, while $S_c$ uses the position of the last text token in its chunk.

Why does a Summary reuse its chunk's last position?Three reasons stack up: (1) it is causal — a Summary may only see its own chunk and earlier text, and the last position does not let it peek at the future; (2) it places the Summary right next to the content it summarizes in position space, consistent with the distance semantics used in Section 10; (3) reusing the position means no extra position bucket and no change to the position-embedding table. The cost is that a Summary shares a position with the last text token of its chunk, so the two can only be told apart by content rather than by position — which is exactly why Section 10 has to distinguish "local text KV" from "boundary Summary KV" as two separate classes of visible entry.

Level two: Summary → Meta (new in C-KSA)

Now the core of the paper. Inside each C-KSA layer, cut the Summary sequence into non-overlapping groups of $k_m$. For the $r$-th Summary in group $g$ ($0 \le r < k_m$), let its normalized layer input be $h_r \in \mathbb{R}^d$ ($d$ being the hidden size). Equation (1) computes three things at once:

$$ k_r = \mathrm{RMSNorm}(W_K h_r), \qquad v_r = W_V h_r, \qquad z_r = A h_r. \tag{1} $$

Take it term by term, because each term plays a different role:

  • $k_r$, $v_r$ — the key and value of this Summary. Note that $W_K, W_V \in \mathbb{R}^{d_{KV} \times d}$ are the backbone's existing projections, not new ones. In other words, what gets pooled is the very pair of KV the model would compute anyway — nothing extra, nothing bolted on.
  • $z_r = A h_r$ — the aggregation logit. $A \in \mathbb{R}^{d_{KV} \times d}$ is an additional learnable projection whose output width is deliberately aligned with $d_{KV}$ (the total key/value width across all heads). This is C-KSA's only new "brain".

One shape detail is worth noting: the RMSNorm is applied independently per attention head. That means the key scales of different heads do not interfere with one another, and aggregation weights can form separately within each head.

Equation (2) then turns these logits into weights:

$$ [\alpha_0, \ldots, \alpha_{k_m-1}] = \mathrm{softmax}_{\text{group}}\big[\, z_0 + B_0,\; \ldots,\; z_{k_m-1} + B_{k_m-1} \,\big]. \tag{2} $$

Three points:

  1. $B_r \in \mathbb{R}^{d_{KV}}$ is a new, learnable intra-group positional bias. It gives "the $r$-th Summary in the group" an identity — without it, pooling would be entirely symmetric with respect to order inside the group, whereas intra-group position does carry information (later Summaries cover more recent content).
  2. The softmax runs over the $k_m$ Summaries, so for each group $\sum_r \alpha_r = 1$ (coordinate-wise). It is a convex combination, so the output naturally lies inside the convex hull of the inputs and cannot blow up numerically through aggregation.
  3. The softmax is taken independently for each feature coordinate (the paper explicitly writes "independently for each feature coordinate"). This is counter-intuitive but important: $\alpha_r$ is not a scalar weight but a vector of width $d_{KV}$. Feature dimension 37 can prefer the second Summary in the group while dimension 38 prefers the fifth. This is what the paper calls dimension-wise aggregation (the same lineage as DeepSeek-V4 (DeepSeek-AI et al., 2026)), and it is why the equations below use element-wise multiplication rather than scalar weighting.

Equation (3) performs the pooling:

$$ \bar{k} = \sum_{r=0}^{k_m-1} \alpha_r \odot k_r, \qquad \bar{v} = \sum_{r=0}^{k_m-1} \alpha_r \odot v_r, \tag{3} $$

Here $\odot$ is element-wise multiplication. The same set of weights aggregates both key and value — a deliberate design choice: if two independent weight sets aggregated K and V, then $\bar{k}$ and $\bar{v}$ could come from different preferences over the Summaries in the group, K and V would no longer be "paired", and both the interpretability and the stability of attention would suffer. Sharing one set of weights guarantees that $\bar{k}$ and $\bar{v}$ describe the same aggregated object.

Finally, Equation (4) attaches position information to the pooled result:

$$ M_g = \big(\mathrm{RoPE}(\bar{k},\, p_g),\; \bar{v}\big). \tag{4} $$

Here $p_g$ is the position of the last Summary in the group. Two deliberate choices live here:

  • RoPE is applied after pooling, not before. If each $k_r$ were rotated first and then summed with weights, the rotations at different positions would mathematically interfere with each other, and the result would be neither the key at $p_g$ nor the key at any real position. Pool first, rotate afterwards, and the Meta entry sits cleanly at $p_g$. $v_r$ is not rotated (standard practice; RoPE applies only to key/query).
  • Take the group's last position. A Meta entry represents "the whole stretch of history covered by these $k_m$ Summaries", and causal attention can only look backwards, so taking the last position means the Meta does not claim to know the future — it is the most conservative choice and the farthest from the current query. This reprises the same design principle as "a Summary uses its chunk's last position" at level one.

Meta is used only inside its own layer and is not passed forward

Right after Equation (4), the paper nails down the foundation the whole method rests on:

Meta entries are used only inside the layer that constructs them; the original Summary states continue to propagate across layers. Therefore $k_m$ can vary freely across C-KSA layers without changing the shared Summary token layout.

That sentence explains how bottleneck (i) from Section 4 is dissolved. Look back: the reason raising $k_s$ is dangerous in KSA is that the Summary is passed forward, so coarsening pollutes every later layer. C-KSA makes the compression product $M_g$ private to its layer — it is a read-only view that is discarded after use, never entering the hidden-state sequence. Consequently:

  • storage for distant history gains another $k_m$-fold saving (a combined $k_s k_m$),
  • while the granularity of the Summary sequence flowing between layers is completely unchanged: later layers still receive Summaries refined at $k_s=8$ granularity,
  • and there is extra freedom: each layer can choose its own $k_m$ (layer privacy imposes no cross-layer consistency constraint), which the paper explicitly lists as a direction for future work.

Now the cost side, which deserves the same clarity. A Meta that is not passed forward is not a "better representation", only a "cheaper read view": what this layer reads from the Meta cannot be inherited directly by the next layer, which must re-compress from the Summaries handed down to it. In addition, the parameters $A$ and $\{B_r\}$ are per-layer ("specific to each layer") but shared across groups ("shared across groups") — a layer has one set of aggregation rules used by all Meta groups, so the parameter overhead is $O(d \cdot d_{KV} + k_m d_{KV})$ rather than multiplied by the number of groups.

Section 10C-KSA part two: three classes of visible KV and attention-mass correction

Three classes of visible KV: one softmax, three sources

For each text query, C-KSA's visible set is assembled from three parts:

  1. local text — the causal prefix of the current chunk, plus the original text KV of up to $W$ complete preceding chunks. This part is full-resolution and lossless.
  2. boundary Summary — the Summaries immediately preceding the local window that have not yet filled a group (fewer than $k_m$ of them). They remain individually visible until their whole group falls outside the window.
  3. remote Meta — every complete $k_m$-group outside the window, represented by one Meta KV entry.
All three classes participate in the same attention softmax.The paper is careful to stress "All three types of entries participate in a single attention softmax" — it is not three attention passes concatenated or blended with weights, but one unified softmax denominator holding entries at three different granularities: local text, boundary Summaries and Meta. That design makes the relative weight between granularities learnable and constrained by a single normalization, with no hand-set mixing coefficient. The price is the problem below.

The problem: compression steals attention mass from the far end

Replacing $k_m$ entries with 1 entry has a purely statistical side effect: the softmax denominator has fewer terms. Even with local logits completely unchanged, the total mass the far end receives after normalization drops — because $k_m$ entries used to contribute $e^{s_i}$ each, and now only one contributes $e^{s}$.

The paper names this phenomenon attention-mass correction, and handles it by adding $\log k_m$ to every Meta logit before normalization:

$$ \exp\big(s + \log k_m\big) = k_m \exp(s). \tag{*} $$

The derivation is one line, but why this particular term is worth spelling out:

  • We want a single Meta entry to stand in for the sum of the $k_m$ Summaries it represents inside the softmax.
  • If the logits of the $k_m$ Summaries in a group have mean $\bar{s}$, together they contribute $k_m e^{\bar{s}}$.
  • For one Meta entry to contribute the same amount we need $e^{s'} = k_m e^{\bar{s}}$, i.e. $s' = \bar{s} + \log k_m$.
  • Because $\log$ and $\exp$ are inverses, addition in logit space is multiplication in probability space — so a single addition suffices, with no numerical trouble from renormalization.
What this term does and does not do.It does not try to recover the intra-group detail lost to pooling (that is information loss, and a constant cannot buy it back); it only corrects the normalization bias introduced by having fewer entries. In one sentence: $\log k_m$ keeps the "remote versus local" share of attention from drifting systematically because of compression. Whether the far end's internal detail is remembered clearly depends on how well the aggregation module learns. The term $+\,\mathbb{1}_{j\in\mathrm{Meta}}\log k_m$ in Figure 3 is exactly this indicator-function form of the correction.

Two implementation details remain:

  • The correction is added only to Meta logits (in indicator-function form); the logits of local text and boundary Summaries are untouched. That guarantees the local window's attention behavior is bit-for-bit identical to the uncompressed case — compression does not change how the near field is read.
  • The paper notes, when later visualizing attention, that the attention probabilities C-KSA produces already include this pre-softmax $\log k_m$ correction. That is a hint for reading figures such as Figure 13: the mass Meta receives is stated on the corrected basis.

Section 11S-KSA: using Summaries as the router and reading only selected original blocks

S-KSA replaces the full attention layer. It has exactly one question to answer: given a text query, which original blocks should I read? Its answer is "let the Summaries work it out for me". The pipeline has three steps: block representation → block scoring → sparse read.

Step one: Summary-guided block aggregation, Equations (5)–(6)

Cut each chunk further into blocks of $b$ consecutive text tokens ($b$ divides $k_s$). For a block $u$, let its normalized layer inputs be $h_1,\ldots,h_b \in \mathbb{R}^d$ and the normalized input of its chunk's Summary be $h_S \in \mathbb{R}^d$. Using one auxiliary attention head of width $d_A$ (head subscripts omitted):

$$ q_S = \mathrm{RoPE}\big(\mathrm{RMSNorm}(W_{Q_A} h_S),\, p_S\big), \qquad k_i = \mathrm{RoPE}\big(\mathrm{RMSNorm}(W_{K_A} h_i),\, p_i\big), \qquad v_i = W_{V_A} h_i. \tag{5} $$

Here $W_{Q_A}, W_{K_A}, W_{V_A} \in \mathbb{R}^{d_A \times d}$ are auxiliary projections private to each S-KSA layer and completely independent of the backbone's attention projections. The positions $p_S$ and $p_i$ follow the original sequence positions, with a Summary still sharing the position of its chunk's last text token.

$$ \hat{z}_u = V^A\, \mathrm{softmax}\!\left(\frac{(K^A)^\top q_S}{\sqrt{d_A}}\right), \qquad K^A = [k_1,\ldots,k_b],\;\; V^A = [v_1,\ldots,v_b]. \tag{6} $$

The direction of Equation (6) deserves a long look, because it is the most counter-intuitive step in S-KSA:

  • The Summary supplies only the query; the block's text tokens supply key and value. The softmax is taken over the block's $b$ text tokens (the paper states this explicitly: "over the block's $b$ text tokens; the Summary supplies only the query").
  • So $\hat{z}_u$ is not "the block's average" but an attention-weighted sum of the block's text, with the weights decided by the Summary. The Summary plays the role of a taste preference — "what does my chunk care about" — used to pick out what matters inside the block.
  • Concatenating the outputs of $H_A$ auxiliary heads gives $z_u \in \mathbb{R}^{H_A d_A}$, the final representation of block $u$, which is also the source of its index key below.
  • All blocks inside the same chunk share one Summary query but each aggregates its own text tokens. This resembles the landmark pooling of HiLS-Attention (Hu et al., 2026), except that S-KSA reuses an existing Summary and inserts no extra landmark token.

Step two: block scoring, Equation (7)

With block representations in hand, a cheap scorer is needed to rank blocks. S-KSA adapts the Lightning Indexer (DeepSeek-AI et al., 2025):

$$ \rho_u = \sum_{h=1}^{H_I} w_h\, \mathrm{ReLU}\!\left(\frac{(q_h^I)^\top k_u^I}{\sqrt{d_I}}\right). \tag{7} $$
  • The Indexer uses $H_I$ query heads of dimension $d_I$ (8 heads × 128 dims at both scales).
  • The normalized layer input $h_t$ of the text query is mapped to $q_h^I \in \mathbb{R}^{d_I}$, along with one scalar weight $w_h$ per head.
  • The block representation $z_u$ is mapped to one index key $k_u^I \in \mathbb{R}^{d_I}$, shared by all heads. This is the key to the cost saving: if every head had its own block key, the number of block keys would be multiplied by $H_I$.
  • $\mathrm{ReLU}$ keeps each head's contribution non-negative (a negative correlation is not treated as "negative importance"), and $w_h$, scaled by $1/H_I$, merges the per-head scores into $\rho_u$.
  • Before scoring, partial RoPE encodes position information into the query at position $t$ and the key at the block's last position — note that it is partial, rotating only a subset of dimensions.
  • One more detail enabled only at 4B: an extra RMSNorm applied to the projected index query/key. Section 3.4 gives the motivation (feature-scale differences between backbones affect index-logit magnitude and optimization) and reports that without it the 4B Indexer loss stays high and remains below the C-KSA+Full parent even after 21.8B tokens, whereas with it only 4.2B tokens are needed to recover to near the parent. 1.9B keeps the original setting for consistency — the paper itself leaves this asymmetry as an open question for future work.

Step three: sparse access, Equation (8)

Given block scores $\{\rho_u\}$, S-KSA selects at most $K/b$ remote blocks ($K$ being the remote budget in original text tokens), and then:

$$ O_t = \mathrm{Attn}\big(q_t,\; [K_{\mathcal{L}_t}, K_{\mathcal{R}_t}],\; [V_{\mathcal{L}_t}, V_{\mathcal{R}_t}]\big), \tag{8} $$

Square brackets denote concatenation along the sequence dimension, $\mathcal{L}_t$ is the set of local positions and $\mathcal{R}_t$ the set of selected remote positions. Three constraints must hold simultaneously, or causality breaks or budget is wasted:

  • Candidate blocks must belong to completed chunks (otherwise a block's content is incomplete);
  • Candidate blocks must fall entirely before the causal local window (otherwise they would be read twice, once locally);
  • The eligible sink blocks at the start of the sequence are kept within this budget, and only the remaining slots are filled by score from high to low.

Attention is then computed by the backbone's original Q/K/V, with a single softmax over local and remote tokens in each head. In other words, the routing score $\rho_u$ is used only to select blocks and does not participate in the attention weighting — inside a selected block, everything is scored by the real q·k as usual. That distinction matters: it makes the main attention numerically identical to dense attention on the selected set.

The cost ledger: where $O(N^2/b)$ comes from

For $N$ text tokens, S-KSA builds about $N/b$ index keys, so there are $b$ times fewer candidate comparisons than a token-level index; the routing cost during prefill is $O(N^2/b)$, while the main attention reads only the in-budget original blocks for each query.

One line of derivation: $N$ queries, each compared against about $N/b$ block keys, computed per head → $O(N \cdot N/b) = O(N^2/b)$. Against the $O(N^2)$ of token-level DSA, that saves exactly one factor of $b$ — which is why the choice of $b$ (Section 12) is the trade-off point between retrieval quality and routing cost.

Section 13KV cache layout, memory analysis, and mechanism comparison

Whether a method can ship ultimately depends on how the cache is laid out and updated. C-KSA's cache design has one hard requirement: every text query must be able to read all of its visible KV entries with a single contiguous slice, avoiding the need to stitch several cache segments together at each step. That requirement determines the entire layout.

12.1 Structure: two components

Each C-KSA layer maintains two parts:

  1. Attention KV Cache — key and value live in two tensors but with identical layouts, ordered along the sequence dimension as: the current chunk, the local text ring, remote history, and finally free slots.
  2. Summary Ring Buffer — holds the Summary KV of the local chunks plus the auxiliary state needed for compression.

On sizes: the current chunk reserves $k_s$ text slots, the local ring reserves $k_s W$ slots (corresponding to $W$ complete preceding chunks), and remote history holds Meta entries plus the Summaries that have not yet filled a $k_m$ group and are waiting to be compressed. The two rings share the same pointer, pointing at the next chunk slot to be replaced.

One rule is easy to overlook but central to understanding the behavior: as long as a chunk is still inside the local window, text queries read its original text KV, not its Summary KV. Only when the chunk is pushed out of the window does its Summary KV enter remote history.

12.2 The five-step update flow (panels a–e of Figure 5)

The paper walks the whole update through a small example with $k_s=2$, $W=4$, $k_m=4$. Panel by panel:

Step by step:

  • (a) Cache layout — a text query reads one contiguous slice of KV (the blue box). The Summary Ring Buffer holds the local chunks' Summary KV and the compression state. The point: visibility is one contiguous stretch of memory, not a concatenation of segments.
  • (b) Text insertion — new text KV is written right-to-left into the current chunk region, so the "filled part" always abuts the local text ring and contiguity is never broken. In the example the incoming $T_{23}$ lands to the left of $T_{22}$, completing chunk 11.
  • (c) Summary insertion — the Summary query at a chunk boundary attends only to the completed chunk's text KV and its own KV. In the example $S_{11}$ sees only $T_{22}$, $T_{23}$ and itself. Note the causality here: a Summary must never see the next chunk's content.
  • (d) Ring update — once both the text and Summary attention are computed, the completed chunk's text KV is copied into the local text ring, and its Summary KV plus auxiliary state go into the Summary Ring Buffer. If the ring is not full, a free slot is used; if it is full, the oldest local chunk is replaced. The replaced Summary KV moves into remote history but its auxiliary state is kept (it will be needed for future compression). In the example chunk 11 replaces chunk 7: $S_7$ goes remote, $S_{11}$ takes its Summary ring slot, and the pointer advances to $S_8$'s slot.
  • (e) Meta compression — once remote history accumulates $k_m$ uncompressed Summaries, they are compressed into one Meta entry. That entry overwrites the group's first slot, and the remaining $k_m-1$ slots are freed for reuse. In the example $S_4$–$S_7$ merge into $M_1$, stored next to $M_0$. The key constraint: after the overwrite the visible KV is still contiguous, so a text query still reads it in one slice.
The clever part of the design is in (e):compression is not "move four entries somewhere new and free four slots" but "write the result in place into the first slot and free the other three". The cost is having to guarantee that a Meta entry's position is still ordered in sequence semantics (the history it represents really does sit around there); the benefit is that the visible region always remains a single contiguous block of memory. This is also why the decode path can use plain SDPA without a gather kernel — Section 13 comes back to that point.

12.3 Memory analysis: Equations (9)–(10)

Let $N$ be the text length, $H$ and $H_{KV}$ the query / KV head counts, $d_h$ the head width, and $w$ the local text window. KSA's main cache term is $2 N H_{KV} d_h / k_s$; C-KSA replaces it, following the compression rules of Section 9, with:

$$ M_{\text{C-KSA}} = 2 H_{KV} d_h \left[\frac{N}{k_s k_m} + O\!\left(\frac{k_s}{W} + W + k_m\right)\right]. \tag{9} $$

Read this expression in two blocks, because their magnitudes are entirely different:

  • The growth term $\dfrac{N}{k_s k_m}$ — linear in $N$, divided by $k_s k_m$. This is the "distant history" part. With $k_s=8$ and $k_m=128$ it is 1/1024 of uncompressed attention at the same KV width.
  • The bounded term $O\!\left(\dfrac{k_s}{W} + W + k_m\right)$ — does not grow with $N$. The paper explains what it corresponds to: local text, the most recent Summaries, and groups not yet full. Each of the three has a source: $W$ is the number of chunks in the local window; $k_m$ is the ceiling on the "uncompressed remainder"; and the $k_s/W$ term comes from the rounding relationship between chunk granularity and window granularity.
The one thing to remember from this analysis:1024× is only the nominal compression factor for distant history; the local and auxiliary terms still exist. At a fixed compression factor the cache is still linear in $N$ — what KSA V2 does is shrink the slope, not turn growth into a constant. Any retelling that claims "the cache no longer grows" has misread it.

Another property is orthogonality: C-KSA preserves KSA's orthogonal relationship with per-position compression (GQA / MLA) — the extra $k_m$ factor simply multiplies the sequence compression, changing neither the number of KV heads nor the representation width. So combinations such as C-KSA+GQA and C-KSA+MLA can be written down directly.

Finally, the overall saving of the hybrid model has a compact expression. Let $f$ be the full-layer fraction; when layer counts and KV widths match:

$$ \frac{M_{\text{C-KSA+Full}}}{M_{\text{Hybrid KSA}}} \simeq \frac{f + (1-f)/(k_s k_m)}{f + (1-f)/k_s}. \tag{10} $$

Substituting $f = 1/4$ (the 3:1 layout) exposes an important structural fact: $f$ remains in both numerator and denominator, so the Full layers cap how much the whole model can save. In plain language — however hard the KSA layers compress, as long as a quarter of the layers still run dense full attention, that slice of cache saves nothing. This is precisely why S-KSA exists: without removing the last dense layer, the numerator of Equation (10) is forever propped up by $f$. ([estimated] example: substituting $f=1/4$, $k_s=8$, $k_m=128$ into (10) gives a ratio $\approx 0.73$, i.e. whole-model cache falls to about 73% — the same direction as the paper's measured 40.4% reduction; the difference comes from the measured basis also including the indexer, auxiliary state and workspace, and from the Full layer's own larger KV width. The 0.73 here and the 40.4% are not the same basis and must not be compared by subtraction.)

The gap between "nominally 73%" and "measured 40.4%" above is not a typo; it is the key to reading the paper's efficiency claim, and it deserves a ledger of its own. The paper's 1024× compression is a nominal figure for remote-history KV (Table 1, §2.3.2), whereas the headline "40.4% lower" is a measured figure for 128K resident cache (Figure 11a, §3.6) — two orders of magnitude apart. Section 14Kernel design: turning the saved FLOPs into actual time

Saving FLOPs algorithmically is not the same as being faster on the wall clock — if the memory access pattern gets worse, or extra gather/scatter is needed, the saved compute is eaten by memory traffic. This section of the paper is about avoiding exactly that.

13.1 The shared execution skeleton: tiled prefill + online softmax

Both C-KSA and S-KSA follow FlashAttention's tiled execution and online softmax (Dao et al., 2022). Let a group of text queries be arranged into $Q_B$ (one or more query tiles), with corresponding output $O_B$. Each box in these matrices represents one token vector: in the query–key grid, blue cells are visible pairs and white cells are masked pairs. The key optimization is that each loaded KV tile $(K_j, V_j)$ is reused on chip across the whole query group, while a per-query mask enforces each query's own visible set.

The significance of this skeleton is that it hands "visibility" entirely to the mask, while KV tile loading is shared and independent of any particular query. As a result, the difference between C-KSA and S-KSA is compressed into two things — how KV addresses are computed, and how the tile visit order is scheduled. Everything else is reused.

13.2 C-KSA: direct mapping from logical intervals to physical addresses, Equations (11)–(12)

C-KSA's layout is regular, so the kernel can work out which KV each query needs with pure arithmetic — no dense mask, and no block-index table held in memory. The approach treats text, Summary and Meta as three separate zero-based index spaces (logical segments): during prefill the text and Summary Q/K/V are interleaved, while the precomputed Meta K/V sit in a separate buffer.

For a text query at position $t$, first define two quantities:

$$ a = \max\!\left(0,\; \left\lfloor t/k_s \right\rfloor - W\right), \qquad g = \left\lfloor a/k_m \right\rfloor. $$

Here $a$ is the first chunk in the local window and $g$ is the number of complete Meta groups before that window. With these two numbers the three logical intervals are closed-form:

$$ I_T(t) = [\,k_s a,\; t+1\,), \qquad I_S(t) = [\,k_m g,\; a\,), \qquad I_M(t) = [\,0,\; g\,). \tag{11} $$

The three intervals correspond exactly to the three classes of visible KV from Section 10. Read them out: $I_T$ is the causal local text (from the window's start to $t$ itself); $I_S$ is the boundary Summaries (from the last complete group before the window up to the window start $a$ — the remainder that has not yet filled a group); $I_M$ is the complete remote Meta groups (from 0 to $g$).

Next comes the mapping to physical positions. For a text index $i$ and a Summary index $j$:

$$ \phi_T(i) = i + \left\lfloor \frac{i}{k_s} \right\rfloor, \qquad \phi_S(j) = j\,(k_s+1) + k_s. \tag{12} $$

These two expressions are two ways of writing the same intuition:

  • $\phi_T$: every $k_s$ text positions the physical address skips one extra slot (the one occupied by a Summary). $\lfloor i/k_s \rfloor$ is simply the number of Summaries inserted so far.
  • $\phi_S$: the physical address of the $j$-th Summary is $j(k_s+1)+k_s$, i.e. "the last of the $j$-th group of $(k_s+1)$ slots". Here $k_s+1$ is the total number of slots per chunk-plus-Summary.
  • Meta indices address the separate buffer directly, with no offset arithmetic.

Once the mapping is done, each query tile knows which KV tile ranges it must visit, and a position-based mask then excludes entries outside that query's visible set. The paper stresses that these intervals and masks are all computed on the fly inside the kernel and occupy no memory — no dense attention mask needs to be stored, and no block-index table either.

13.3 C-KSA: prefill integration and decode

During prefill, the text-query kernel carries each query's online-softmax state continuously across the text, Summary and Meta segments (the implementation counterpart of the three entry classes sharing one softmax), and applies the $\log k_m$ correction to Meta logits only. A separate local kernel makes each Summary query attend over its own chunk's text and its self-KV. Both kernels write their outputs straight back into the interleaved physical positions.

The decode stage needs almost nothing special: the cache layout of Section 13 has already placed the visible KV in one contiguous region, so standard scaled dot-product attention (SDPA) works directly, with no gather.

Equations (11)–(12) and the layout of Section 13 are two faces of the same thing.The layout guarantees "the visible KV is contiguous"; the mapping formulas guarantee "it can be found arithmetically". Neither suffices alone: with only the former, the kernel still has to scan for boundaries; with only the latter, the fast path degrades into repeated non-contiguous reads. This is the tightest instance in the whole paper of algorithm, layout and kernel working together.

13.4 S-KSA: fused scoring plus sparse tile scheduling

Fused block scoring. If one kernel computed the dot products and another did the multi-head aggregation, the intermediate scores would have to make a round trip through memory. To cut that traffic, S-KSA uses a fused kernel that does the dot product and the weighted multi-head score merge on chip in one pass. In Figure 7b, $Q_I$ is the stacked query matrix of the indexer heads and $K_I$ their shared block keys (the superscript $I$ denotes the indexer); in the grayscale matrix rows are queries and columns are candidate blocks, darker meaning higher score; selection then happens within one kernel: under a budget of $K$ tokens (i.e. at most $K/b$ blocks), remote blocks are chosen independently for each query, and each row of the blue matrix on the right is one query's block-index list.

What does "fused" save here?It saves the write and read-back of that $Q \times \text{number of blocks}$ intermediate score matrix. At 128K with 32768 blocks that matrix is substantial even at reduced precision — and it is a pure intermediate, so writing it out and reading it back contributes nothing to the result. After fusion the scores are produced on chip, aggregated on chip, and Top-$K$ is done on chip; only the final block indices need to land in memory.

KV-tile scheduling. For each group of queries, the selected remote blocks and the local window are mapped onto KV tiles to build a conservative schedule. The schedule skips KV tiles that nobody accesses, while block selection, local visibility and causality are all handled by the per-query mask inside the tiles that are scheduled. The schedule and the mask are handed directly to FlashAttention's forward kernel, which runs the tiled prefill.

A custom sparse kernel for decode. During decode, first gathering the selected KV entries into a temporary buffer and then computing attention would pay an extra round of reads plus a round of writes. To sidestep that cost, S-KSA uses a custom sparse kernel that reads directly from the KV cache according to the selected block indices.

Regrouping the three items in this section by "what they save" makes it clearer:
• Fused scoring saves the memory round trip of intermediate scores (bandwidth).
• Tile scheduling saves the compute and loads spent on empty tiles (compute + bandwidth).
• The custom sparse kernel saves the extra reads and writes that gathering would cost (bandwidth).
None of the three reduces the "mathematical number of multiplications"; all three reduce movement. That is exactly where long-context inference ends up bottlenecked, and why this section deserves to exist on its own.

Finally, putting Sections 13 and 14 together leaves one qualitative conclusion worth remembering: KSA V2's remaining main cost is the original-text KV kept by the sparse layers — the incarnation, under the new architecture, of the $f$ term in Equation (10). The paper names it in the conclusion as a natural next direction.

Section 15Experimental setup and the adaptation protocol: converting an existing model into KSA V2

The experimental section states its problem setting clearly from the start: it does not train a new architecture but asks a retrofit question — can continued pretraining adapt an existing Hybrid KSA to more aggressive KV compression and sparse original-text access while preserving its original capabilities. The route is to validate C-KSA with Full attention first, then layer S-KSA onto the compressed backbone, and finally evaluate along three lines — retrieval, general capability and inference efficiency — with additional ablations on compression granularity, block size, teacher pooling, routing scheme and backbone choice. Unless stated otherwise, all experiments and analyses run on the 1.9B model.

The starting point is the 128K checkpoints of 1.9B and 4B Hybrid KSA from the KSA report. The 1.9B backbone is 24 layers of MHA; the 4B backbone is 36 layers of GQA with 32 query heads and 8 KV heads. Both use the 3:1 interleaving of three KSA layers to one Full layer, and both insert one Summary every $k_s = 8$ text tokens. Two variants are evaluated: C-KSA+Full compresses the remote Summary KV into Meta entries inside the KSA layers; C-KSA+S-KSA goes further and replaces the Full layer with S-KSA, i.e. block-sparse original-text attention. Notably, C-KSA supports per-layer compression configurations in the method, but the paper explicitly states that every evaluated configuration uses a uniform $k_m$ across C-KSA layers — a point that returns in the "worth testing next" list below.

Evaluation follows the KSA report's protocol: long context uses RULER at sequence lengths from 4K to 128K; general capability covers knowledge (MMLU, CMMLU, C-Eval, MMLU-Pro), mathematics (GSM8K, CMATH, MATH) and code generation (MBPP, HumanEval, reporting pass@1), nine benchmarks in total. Baselines reuse KSA's from-scratch results (1.9B) and continued-pretraining results (4B), including Full, Hybrid SWA, Hybrid SCA, Pure KSA and Hybrid KSA, with Hybrid GDN added at 1.9B and Hybrid Linear at 4B. Hybrid KSA is positioned as the parent model for "capability preservation", and Full as the dense-attention reference; training data follows KSA's corpus and mixture, with the context length fixed at 128K.

On the reference point, the paper does something important: it specifically tests whether continued pretraining of the parent model can serve as a stronger control. See the Table 11 discussion at the end of this section — under the tested recipe and data budget, continued pretraining of the unmodified Hybrid KSA brings no consistent RULER improvement, so the paper is entitled to use the original checkpoint as the quality reference. The argument is not glamorous, but it closes off the objection that "you trained more, so you got better".

Start with the backbone and module configuration at the two scales (the full configuration is in Table 2 in Section 12 and is not repeated here). 1.9B is a 24-layer MHA with hidden 2048 and intermediate 6144, 16 query heads and 16 KV heads; 4B is a 36-layer GQA with hidden 2560 and intermediate 9728, 32 query heads and 8 KV heads. Both have head dimension 128, a 3:1 ratio and $k_s$ of 8. The largest divergence is in the C-KSA and S-KSA module configuration: 1.9B uses $k_m = 128$ with KV width $d_{KV} = 2048$, while 4B uses $k_m = 32$ with $d_{KV} = 1024$.

Looking at the stage budgets in Table 3 shows how "cheap" this conversion is. C-KSA's added parameters are the aggregation projection and positional bias at each scale, 80.2M for 1.9B and 71.7M for 4B; S-KSA's auxiliary attention, Indexer and routing-related parameters are 86.6M for 1.9B and 163.0M for 4B. Against the backbone sizes of 1.9B and 4B these are single-digit-percentage increments, and the inference payoff shows up in the efficiency section later.

The adaptation route above is drawn as a pipeline in Figure 8. Start with the module setting — "module settings apply where the corresponding modules are used" is not a throwaway phrase: during the module-only stage only the newly introduced aggregation projection $A$ and positional bias $\{B_r\}$ are trained (and in the S-KSA stage, the new aggregation module and Indexer), with every inherited parameter frozen; the full-parameter stage is what opens up the whole model. C-KSA goes "module-only → full-parameter", whereas the S-KSA stage is module-only only.

The whole route condenses into one sentence: each adaptation segment solves only for one newly introduced module, and each hyperparameter sweep happens after the previous step is fixed. The cost is more experiment rounds (6 compression granularities × 3 sparsity settings); the benefit is that conclusions from different steps do not contaminate one another.

Section 16The two-stage loss: align the outputs first, then open up the whole model

The greatest fear when adapting a pretrained model is "open it up and everything previously learned gets washed away". KSA V2's answer is to split into two stages: first let the new modules align their outputs with the uncompressed version, and only once alignment is achieved open all parameters for ordinary language modeling. This passage is worth reading equation by equation.

The module-only stage trains the aggregation projection $A$ and the positional bias $\{B_r\}$, with all inherited parameters frozen. The new parameters are initialized to zero, so at initialization the aggregation weights are uniform (which is also why an alignment loss is needed: uniform aggregation cannot reproduce the information of so many Summary entries). Let $O^{C}_{l,t,d}$ and $O^{K}_{l,t,d}$ be the attention outputs of C-KSA and uncompressed KSA at layer $l$, text position $t$ and coordinate $d$, both computed from the same input at the same layer and both taken before the output projection. The alignment loss is a per-coordinate squared error (clipped, then averaged):

$$ \mathcal{L}_{\text{align}} = \frac{1}{|\mathcal{I}_C|\,|\mathcal{T}|\,D} \sum_{l \in \mathcal{I}_C} \sum_{t \in \mathcal{T}} \sum_{d=1}^{D} \min\!\left( \left( O^{C}_{l,t,d} - \mathrm{sg}\!\left( O^{K}_{l,t,d} \right) \right)^2,\ 0.1 \right) $$

Here $\mathcal{I}_C$ is the set of C-KSA layers, $\mathcal{T}$ the text positions in a minibatch, $D$ the concatenated attention width, and $\mathrm{sg}(\cdot)$ denotes stop-gradient. Three design details are all practical: the error is measured per coordinate rather than per vector, so no norm-scale choice is involved; each error is clipped at an upper bound of $0.1$, preventing individual outlier coordinates from dominating the gradient; and the stop-gradient on the reference side ensures gradients flow only back into the new modules and never drag the frozen KSA side along.

After alignment completes, the full-parameter stage begins and the objective falls back to plain language modeling:

$$ \mathcal{L}_{\text{comp}} = \begin{cases} \mathcal{L}_{\text{CE}} + \lambda_{\text{align}} \mathcal{L}_{\text{align}}, & \text{module-only adaptation}, \\ \mathcal{L}_{\text{CE}}, & \text{full-parameter adaptation}, \end{cases} \qquad \lambda_{\text{align}} = 5 $$

In other words, the alignment loss exists only during the module-only stage, with weight 5; once the whole model is opened up it is dropped entirely, leaving only cross-entropy. Why this order rather than joint training from the start? One direct reading: if the whole model were opened up from the beginning with the alignment term applied, the frozen reference $O^{K}$ would itself be moving, making alignment a moving target, and the language-modeling gradient would immediately rewrite the KSA side's representations, leaving "alignment" without a well-defined reference point. Pulling the new modules to a point approximately equivalent to the original behavior first, and only then opening the model, is equivalent to continuing training from a point already close to the original model — minimal forgetting risk. This also dovetails with Table 3's "the optimizer and learning-rate schedule are re-initialized at every stage switch": stage boundaries are treated as fresh starts rather than one continuous annealing run.

The S-KSA stage has a different objective structure: it is a distillation problem rather than a regression one. During training the Full layer still keeps dense attention, and the probabilities it computes supervise block selection. For a query $t$, let $\mathcal{U}_t$ be all eligible remote blocks, $\mathcal{B}_u$ the text positions inside block $u$, and $a_{t,i}$ the dense causal attention probability after averaging across backbone heads. Then the block-level teacher distribution $p_t$, the Indexer distribution $\pi_t$ and the training objective are:

$$ p_{t,u} = \mathrm{sg}\!\left( \frac{\max_{i \in \mathcal{B}_u} a_{t,i}}{\sum_{v \in \mathcal{U}_t} \max_{j \in \mathcal{B}_v} a_{t,j}} \right), \qquad \pi_t = \mathrm{softmax}(\rho_t), \qquad \mathcal{L}_{\text{S-KSA}} = \mathbb{E}_{l,t}\!\left[ D_{\mathrm{KL}}(p_t \,\|\, \pi_t) \right] $$

Here $\rho_t$ is the Indexer score defined by Equation (7), taken over all blocks in $\mathcal{U}_t$, and $\mathrm{sg}(\cdot)$ is again stop-gradient. The loss is averaged over valid text queries within each adapted layer, then averaged across layers. Two points are worth calling out: first, the teacher takes the maximum within the block (max pooling) after averaging across heads, which the paper says follows QSA and which it contrasts against sum pooling in Section 3.7; second, $\pi_t$ exists only during training — at inference the trained Indexer selects blocks directly and the routing scores are never used as extra attention weights; the main attention still performs a single softmax over the selected original tokens and the local window.

Why align first and open up later [organized]:putting the two losses side by side shows the paper is decoupling two things that interfere with each other — "the new modules' outputs should resemble the old modules'" and "the whole model should keep learning language modeling". The former is a regression/distillation problem with a well-defined reference, well suited to fast convergence while the other parameters are frozen; the latter needs all parameters to cooperate and is best done without extra constraints. Doing them in stages staggers the two optimization problems instead of letting them pull against each other within the same batch of gradients.

There is one more practical difference that is easy to miss: the S-KSA stage has the largest token budget of the three — 18.5B tokens at 1.9B, whereas C-KSA's two stages together come to only 10.1B. In other words, the paper spends most of its adaptation budget teaching the Indexer how to select blocks, not on the compression module. That budget allocation alone says something about how hard sparse routing is.

Section 17Model quality: how much is preserved at 1.9B and 4B

Start with the conclusion, on Table 4: at 1.9B the six-length RULER mean of C-KSA+S-KSA is 72.39%, against 72.61% for the parent Hybrid KSA and 67.55% for Full; at 4B the numbers are 84.15%, 84.45% and 83.69%. In other words, the adapted model essentially preserves the parent's retrieval ability (0.22 percentage points behind at 1.9B, 0.30 at 4B) while staying clearly ahead of Full. But this is not "lossless" — the 128K point has both gains and losses, and general capability pays a measurable price. Take them one at a time.

Spreading RULER out length by length makes "what was preserved and what was lost" clearer. Relative to the parent Hybrid KSA, C-KSA+S-KSA is higher at 4K (81.48 vs 80.65) and 16K (75.67 vs 74.07), roughly level at 8K (72.42 vs 73.35, slightly lower), and lower by 1.52, 0.96 and 0.34 percentage points at the three long lengths 32K, 64K and 128K. That is, the loss is concentrated in the 32K–64K band, while 128K is actually held very tight. Against the pure Full attention reference its advantage is overwhelming: Full scores only 48.75 at 128K, 16.26 percentage points below C-KSA+S-KSA.

The C-KSA+Full column deserves its own paragraph (Figure 9(a) gives its recovery curve). It keeps the Full layers and only compresses the remote Summary from $k_s = 8$ to $k_s k_m = 1024$ inside the KSA layers; its mean of 72.68 is even slightly above the parent's 72.61, and its 128K score of 66.31 is above the parent's 65.35. That is a clean single-factor conclusion: 1024× compression of remote history by itself costs almost nothing in retrieval. The cost only appears when S-KSA is layered on — 128K falls from 66.31 to 65.01. And applying the same sparse adaptation to an uncompressed Hybrid KSA takes 128K from 65.35 down to 61.06 (Table 9(c)). Measured against their respective dense references, the drops are 1.30 and 4.29 percentage points: a compressed backbone is actually more resilient to sparse adaptation.

Reading Figure 9 together with the budgets in Table 3 reveals something counter-intuitive: the module-only stage (training only 80.2M new parameters) already pulls retrieval scores back substantially from the low point introduced by compression, and the later full-parameter stage contributes "approaching" rather than "turning things around". This echoes the oracle experiment in Section 3.7 — if the selection is accurate enough, the backbone does not even need updating.

On general capability the paper's wording is "broadly comparable": relative to Hybrid KSA, C-KSA+S-KSA is higher on three of the nine items (MMLU 47.09 vs 46.83, MMLU-Pro 22.83 vs 22.52, CMATH 63.50 vs 61.83) and lower on the rest, with the largest drop being 2.81 percentage points on GSM8K, and MBPP and HumanEval lower by 1.20 and 1.83 points respectively. Against C-KSA+Full, adding S-KSA changes every item by no more than 1.83 percentage points, with gains and losses both present, indicating that sparse adaptation is not the cause of a systematic decline. Against Full it wins eight of the nine items, the only exception being C-Eval (42.94 vs 44.28).

1.9B summary:the "compression" step is close to free (mean +0.07, 128K +0.96 relative to the parent — both gains), while the "sparsity" step costs a little retrieval (128K −1.30), with one- or two-point fluctuations on general capability. Every cost appears after the Full layer is also replaced, not from compression itself.

The 4B experiments (Table 5) answer a different question: does this conversion transfer to a GQA backbone with shared KV heads? The configuration is $k_m = 32$ and $b = 4$; with $k_s = 8$, C-KSA compresses remote KV 8 × 32 = 256-fold along the sequence dimension while keeping GQA's shared KV heads. The token budget is 6.7B module-only + 15.9B full-parameter, followed by 4.2B of S-KSA module-only; the remote budget, local window and sink settings match 1.9B; the only architectural difference is that 4B's Indexer additionally normalizes the projected query/key.

The 4B reversal at 128K is worth noting. At 1.9B, adding S-KSA takes 128K from 66.31 down to 65.01; at 4B the same action takes 128K from 73.92 up to 74.41. "Sparsity always costs points" is not a general rule — it is decided together with the backbone, the data budget and the Indexer configuration. The mean row, however, still slips slightly (84.15 vs 84.45), with the drag coming mainly from 8K, 16K and 32K (87.78 / 85.45 / 83.60, against the parent's 90.53 / 88.86 / 86.65), while both 4K (93.38 vs 92.97) and 64K (80.28 vs 76.04) rise.

On general capability the paper's figures are: C-KSA+S-KSA stays within 0.40 percentage points of C-KSA+Full, and 0.50–2.58 points below Hybrid KSA. C-KSA+Full is itself already somewhat below the parent (for example MMLU 68.79 vs 70.50), so this loss comes more from the full-parameter training of the compression stage than from the sparsity stage.

Then there is the setting that was "only added afterwards" — Indexer Q/K normalization. The paper candidly reports a controlled comparison: without Q/K normalization, 4B's Indexer loss stays high, and even after 21.8B adaptation tokens RULER remains below its C-KSA+Full parent; under the same adaptation setup, normalizing the projected query/key recovers to near the parent with only 4.2B tokens. The paper's explanation is that feature-scale differences between pretrained backbones affect the magnitude and optimization of index logits, and RMSNorm reduces that scale sensitivity. Even more worth recording is the boundary the paper draws itself: 1.9B keeps the original setting and was not re-run through the full experimental suite with this change; whether normalization would similarly reduce the adaptation data needed at 1.9B is explicitly left as an open question. That is an honest gap and a very concrete reproduction risk.

Finally, the choice of compression granularity at 4B. Table 6 compares $k_m \in \{8, 16, 32, 64, 128\}$ under one identical budget (6.7B module-only + 15.9B full-parameter for every configuration).

Read Table 6 together with Table 9(a) and the difference in granularity sensitivity between the two scales is plain: at 1.9B, sweeping $k_m$ from 4 to 128 moves the RULER mean only within 71.92–72.74, with no systematic decline; at 4B, sweeping from 8 to 128 gives means between 82.46 and 83.94, with the optimum at $k_m = 8$. The paper offers a conjectural explanation for the 1.9B insensitivity: the Full layers can still read the original-text detail lost in compression, so the effect of compression granularity is diluted. On the 4B side, the reason for choosing $k_m = 32$ is the benefit/cost ratio — four times more compression for almost no loss.

Section 18Long-context retrieval analysis and inference efficiency

Mean scores hide differences along the position dimension, so the paper adds a NIAH grid (Figure 10) and a paired 128K subtask table (Table 7). Start with the grid: across six context lengths (4K to 128K) × eleven insertion depths (0% to 100%), it compares the models on identical inputs.

Beyond the grid, Table 7 makes a paired comparison on six RULER-128K subtasks. There is both good news and clear bad news here.

Failure mode (recorded honestly):FWE's 45.00 → 26.67 is an absolute drop of 18.33 percentage points, close to a halving, and it is not noise-level fluctuation. The paper mentions it in two places: the contributions section writes that "aggregation-heavy tasks such as frequent-word extraction degrade under block selection", and the Failure mode discussion in Section 3.7 gives the quantitative form — "the largest 128K subtask drop is frequent-word extraction, from 45.00% to 26.67%, which is an aggregation task". So the paper identifies the phenomenon and attaches a causal label (aggregation task), but offers no mechanism-level explanation and no fix for this class of task. Combined with the direction of the other five items in Table 7, a reasonable reading ([organized] on this page, not a paper conclusion) is that block-level sparse selection picks "a few high-weight positions", which is inherently unfavourable to tasks that require a statistical accumulation over the whole context, since aggregation needs information spread more diffusely. This thread is also worth connecting to the entropy-corrected chunk weights of HiLS-Attention in Section 20 — that work is precisely about applying an entropy correction to block weights.

At the same time, fairness requires saying this: FWE's absolute level was already low (the parent scores only 45.00), and on VT both models sit around 25 (25.00 → 23.00). Both are hard tasks at 128K for both models, so the correct reading of this table is "sparse adaptation is a net gain on retrieval-type tasks and needs extra care on aggregation-type tasks", not "degradation overall".

Next is efficiency (Figure 11), which is also KSA V2's main selling point. The measurement basis must be stated first: a 1.9B model, BF16, batch size 1, a single NVIDIA H800, sequence length from 16K to 128K, with C-KSA+S-KSA using $k_m = 128$ and $b = 4$. The cache measurement includes the indexer, auxiliary state, KV storage and resident workspace.

Cache. At 128K the resident cache of C-KSA+S-KSA is 6.31 GiB, against 10.59 GiB for Hybrid KSA and 24.00 GiB for Full, reductions of 40.4% and 73.7% respectively. The 40.4% figure is the same basis as the abstract's "reduces resident cache size by 40.4%". One caution: the 6.31 GiB here is not a purely theoretical value — it includes the indexer, the auxiliary compression state and the resident workspace, i.e. the net result after C-KSA's extra overhead has been counted in.

Prefill. At 128K C-KSA+S-KSA reaches 44,971 tokens/s, against 29,837 for Hybrid KSA and 20,830 for Full, equivalent to 2.16× Full. The gain over Hybrid KSA grows with length: 1.23× at 16K, widening to 1.51× at 128K. That shape is reasonable — the payoff of sparse access naturally amplifies as sequences get longer.

Decode. C-KSA+S-KSA reaches 215.50 tokens/s at 16K and 198.85 tokens/s at 128K, against 162.87 and 157.02 for Hybrid KSA; across the four sequence lengths the speedup range is 1.23–1.32×. The abstract's figure of "1.27× decode throughput" falls inside that range. Separately, the overall basis given in Figure 1 is per-token inference FLOPs and cache size lower by 2.3× and 2.9× (relative to the reference set), consistent in direction with this section but on a different basis — do not mix the two when quoting.

The paper also gives a finer compute ledger: at 128K, C-KSA+S-KSA's estimated matrix FLOPs per text token is 6.38 times lower than Full and 2.76 times lower than Hybrid KSA; the BF16 KV cache and index-key cache are smaller by 3.86 times and 1.35 times respectively. That last 1.35 is worth noting — the index-key cache is itself a non-trivial size, not zero. In addition, under the same settings as Table 7, C-KSA raises the remote-history compression rate from $k_s = 8$ to $k_s k_m = 1024$.

Efficiency summary:the 40.4% resident cache reduction, 1.51× prefill and 1.23–1.32× decode at 128K were all measured under the same 1.9B / BF16 / batch=1 / single-H800 basis. That basis is also the boundary of these numbers: batch size 1 means continuous batching is not covered, which Section 21 lists as something worth testing next.

Section 19Analysis and ablations: hierarchical compression, routing choices, and the oracle experiment

This is the densest section of the paper. It answers four questions: is hierarchical compression better than simply enlarging the chunk? How large should $k_m$ be? How should the sparsity scheme and teacher pooling be chosen? And the most important one — if selection is accurate enough, does the backbone need changing at all?

Question one: direct coarse granularity versus hierarchical compression. To reach 1024× remote compression, a simpler route is to set the Summary chunk straight to $k_s = 1024$. Table 8 compares that one-step route with C-KSA's two-level compression, all retaining the Full layer; the large-chunk model is trained from scratch, while C-KSA is built on a $k_s = 8$ Hybrid KSA.

The paper's explanation for the gap is "extra computation": C-KSA uses a summary chunk of 8, which introduces more tokens at the input sequence level, and the compressed KV then passes through an additional module, effectively performing a two-step summary. The paper also notes this agrees with the 4B conclusion in the KSA report — raising $k_s$ from 8 to 64 drops the 4K–64K RULER mean from 82.97 to 77.79. Putting this in the experimental section is valuable: it shows that "compressing harder" and "compressing in one step" are not the same thing, and that keeping a fine-grained intermediate representation pays off.

Question two: how large should $k_m$ be. Table 9(a) sweeps $k_m \in \{4, 8, 16, 32, 64, 128\}$ on C-KSA+Full, with the six-length RULER mean landing between 71.92 and 72.74 and no systematic decline as compression increases. The paper's conjecture is that the Full layers still provide access to the original-text detail that compression removes. The reason for choosing $k_m = 128$ is marginal return: at 128K with $k_m = 128$ each layer holds only about 128 Meta entries, and compressing further saves little cache, so higher compression ratios are left for million-token contexts.

Question three: block size and routing scheme. Panel (b) compares S-KSA with $b \in \{2, 4, 8\}$, token-level DSA, and Qwen Sparse Attention (QSA) on the same backbone. QSA offers a simpler alternative: average the projected token-level index keys within each block. The paper aligns QSA with its own settings by using $b = 4$ and 8 indexer heads, following Qwen's QSA indexer design. The result: $b = 4$ matches $b = 2$ and token-level DSA in mean score while having half and a quarter of their routing candidates respectively, and it beats QSA at the same block size (mean 72.39 vs 71.34, 128K 65.01 vs 61.39). Pushing on to $b = 8$ reduces candidates further but degrades retrieval noticeably, with 128K at only 57.62. So $b = 4$ is the compromise between retrieval quality and routing cost.

Also, in this panel the paper reports RULER only, for a reason it states plainly: most general-capability sequences already fall within the combined remote-plus-local budget, so they discriminate poorly between routing qualities. That is a methodologically defensible choice, but it also means this table cannot be used to infer general capability.

Teacher pooling. With $k_m = 128$ and $b = 4$, the paper contrasts the max-pooled teacher of Equation (15) (following QSA) against a sum-pooled teacher (using $\sum_{i \in \mathcal{B}_u} a_{t,i}$ as the block weight), with the two training runs differing only in pooling: max pooling lifts the mean from 71.49% to 72.39% and 128K from 61.68% to 65.01%. The paper's explanation is that retrieval depends on a few salient tokens whereas sum pooling dilutes them with diffuse attention, and the result also confirms that QSA's choice holds on a KSA backbone.

Question four: does the backbone need changing. Table 9(c) compares the same S-KSA adaptation ($b = 4$, max-pooled teacher, 18.5B tokens module-only, identical remote budget / local window / sink) applied on Hybrid KSA and on C-KSA+Full: C-KSA+S-KSA gives a mean of 72.39 and 65.01 at 128K, while KSA+S-KSA gives 71.84 and 61.06. Against their respective dense references, the 128K drop is 1.30 percentage points on the C-KSA side and 4.29 on the Hybrid KSA side. Figure 12(c) offers a complementary observation: at the same token budget, oracle block selection retains slightly more decode attention mass on C-KSA than on Hybrid KSA (including local context and sinks), consistent with the smaller retrieval loss after sparse adaptation.

Figure 12 and Table 10 record the most persuasive experiment of all: freeze every parameter and select using Full attention probabilities directly. Token selection ranks by individual probabilities; block selection takes the maximum probability within each $b = 4$ token block, matching the Indexer's teacher pooling rule. The paper calls this oracle selection and compares it against the unmodified Full layer on the same backbone. The remote budget $K$ includes 8 sink tokens, and a 1024-token local window is retained separately.

The argumentative force of these numbers comes from how cleanly they cut: if the selection is accurate enough, not even backbone adaptation is needed, and retrieval performance recovers essentially to dense levels. Two conclusions follow: first, accurate selection alone recovers near-dense RULER without any backbone update, including on a model already adapted to C-KSA; second, full-parameter sparse continued training brings no clear RULER improvement under the recipe and budget the paper tested. Together they support concentrating sparse-adaptation effort on the aggregation module and the Indexer rather than on changing the backbone.

The attention-mass part is more intuitive: at $K = 4096$, the selected remote tokens plus the 1024-token local window cover only about 3.9% of a 128K context, yet retain 82.83% of decode attention mass, with a corresponding RULER of 66.24 against dense attention's 66.31 — a gap of 0.07 percentage points. At the same budget Hybrid KSA retains 81.71%. The paper adds a key qualification: local context and sinks alone already retain a considerable share of attention mass, yet retrieval performance is poor, which in turn shows that "selecting the relevant remote content" is what makes sparse attention viable, not the retained-mass number itself.

The last set of visualizations grounds all of this in a concrete example. Figure 13 compares per-layer attention and block selection between Hybrid KSA and the main model C-KSA+S-KSA on the same 16K NIAH sample (the latter with $k_m = 128$, $b = 4$, $K = 4096$); both retrieve the answer correctly from outside the local window.

The "shallow versus middle-and-deep" difference in Figure 13 is interesting ([organized] on this page): Meta entries are barely used in the shallow layers (7.7–13.7%) and only become dominant in the middle and deep layers (73.1–87.8%). This agrees with the common observation that shallow layers rely more on local, fine-grained information while deep layers do coarse integration, and it hints that using the same $k_m$ at every layer may not be optimal — but the paper runs no per-layer-$k_m$ experiment on that basis, which is left to Section 21.

Finally there is the control experiment that establishes the legitimacy of the reference point (Table 11). Because the adapted models receive more training than the baselines, the paper needs to rule out the "more training is just better" explanation, so it performs full-parameter continued pretraining of the unmodified Hybrid KSA from the same 128K checkpoint (global batch 256, peak learning rate $4 \times 10^{-4}$, warmup–stable–decay schedule).

The paper's conclusion is that under the tested recipe and data budget, continued pretraining does not give Hybrid KSA a consistent RULER improvement, so using the original checkpoint as the quality reference is justified. That argument is crucial to the credibility of the whole paper — it turns the most easily challenged point, "you trained more", into a testable control, and it honestly reports the result that additional training slightly hurts.

Key points of this section:(1) at the same 1024× compression rate, hierarchical compression at 72.68 beats direct coarse granularity at 70.63; (2) $k_m$ is insensitive at 1.9B (71.92–72.74), and 128 is chosen for marginal cache benefit; (3) $b = 4$ is the quality/cost compromise and $b = 8$ is clearly worse (69.79); (4) max pooling beats sum pooling (128K 65.01 vs 61.68); (5) the oracle experiment proves that "selecting accurately" alone approaches dense performance (66.24 vs 66.31) and the backbone need not change; (6) the 3.9% of positions → 82.83% of attention mass figure is the core of why S-KSA is viable.

Section 20Lineage of each component: where every piece comes from

KSA V2 is not an architecture grown from nothing; it grafts two modifications onto an existing hybrid backbone, each drawing on several existing lines of research. The paper marks every such borrowing explicitly, and this section collects those marks so it is clear what is inherited and what is this generation's own choice.

Start with the positioning of the main line. The Summary token mechanism itself comes from KSA (Chu et al., 2026), and Hybrid KSA's 3:1 layer interleaving comes from the same paper; KSA V2 leaves the layer structure alone and changes two components — C-KSA further compresses the Summary KV of distant history, and S-KSA replaces dense attention over original text with Summary-guided block sparsity. So the table below reads: "Upstream" is the provenance the paper itself labels, and "This generation's change" is what KSA V2 does differently from that provenance. Read the table vertically and two fairly clear lines of difference emerge.

The first: no new tokens. H-SSA adds meta-gist tokens, Landmark Attention adds landmark tokens, HiLS-Attention adds landmark queries — all of these upstream schemes insert new structure into the sequence. Both C-KSA and S-KSA in KSA V2 reuse existing Summaries: a Meta entry exists only inside the layer that constructs it and is never passed forward, and the routing block representations are computed on the fly from existing Summaries and block tokens. The direct benefit is that the Summary layout is unchanged, so the conversion retrofits onto an already-pretrained Hybrid KSA without touching sequence length — which is the technical basis for the paper listing "retrofit-friendly" as a selling point.

The second: routing scores do not enter attention. NSA uses learned block compression to guide fine-grained selection and fuses compressed, selected and local attention paths; HiLS-Attention merges intra-block outputs with entropy-corrected chunk weights; SAS learns context ranking inside the attention normalization. All of these let the routing signal participate in weighting the final output. S-KSA separates the two: the Indexer's scores decide only which blocks to read, and the main attention then performs one softmax over the selected original tokens and the local context. The paper states this explicitly in Related Work, and it is one of the preconditions for S-KSA and C-KSA coexisting on the same tiled execution path.

Whether the upstream methods mentioned match the versions cited, and whether the paper's descriptions of each upstream method are accurate, have not been checked item by item on this page. To judge the boundary of novelty from this table, go to the original references.

Also worth noting is the paper's own positioning: in Related Work it takes care to distinguish itself from DeepSeek-V4's CSA (the main attention never reads compressed text) and from DSA (routing drops to block granularity rather than token granularity). These two differences are not rhetoric; they correspond to two observable results in Section 19 — reading original text in the main attention is the precondition for RULER to approach the dense reference, and block-granularity routing is the source of a 4× reduction in candidates with no loss in the mean.

Section 21Commentary: strengths, limits, and the gaps worth testing next

This is a strongly engineering-oriented technical report: it proposes no new attention mechanism, but separately removes two bottlenecks of an existing hybrid architecture (the compression rate welded to chunk size, and the Full layers still paying quadratic cost), and treats "did the conversion damage existing capability" as a first-class question. Below are strengths and limits, followed by a separate list of "not disclosed, worth testing next".

Strengths

1. Retrofit-friendly, with quantifiable cost.Both new components reuse existing Summaries, add no tokens and change no Summary layout, so they attach directly to a pretrained Hybrid KSA. The price is stated concretely: C-KSA adds 80.2M parameters at 1.9B and 71.7M at 4B; S-KSA adds 86.6M and 163.0M respectively; the adaptation token budget at 1.9B is 6.7B + 3.4B + 18.5B. That is a list you can budget against directly, far more useful than an adjective like "lightweight adaptation".

2. One set of Summary tokens reused in two roles, without increasing input length.As memory it is compressed into layer-local Meta entries; as an index it is used to build block-level routing representations. The paper states this modestly, but it really is the most elegant design choice in the paper — because no tokens are added, the two conversion routes stack on each other without conflict and can coexist on the same tiled prefill execution path.

3. Hierarchical compression beats directly enlarging the chunk, and the paper provides the control.Table 8 compares "one step" against "two levels" at the same 1024× remote compression rate: 70.63 vs 72.68, a gap of 2.05 percentage points. That conclusion is directly useful to anyone working on KV compression — it shows the shape of the compression path (how many levels, how coarse each one) is itself a design variable to tune, not just the final ratio. The paper also offers a plausible explanation: a two-step summary preserves a fine-grained intermediate representation.

4. S-KSA is more resilient on a compressed backbone, and the paper cuts the causality with an oracle experiment.Relative to their respective dense references, the 128K drop is 1.30 on the C-KSA side and 4.29 on the Hybrid KSA side. More important is Table 10: with every parameter frozen and oracle block selection driven by Full attention probabilities, the mean on all five backbones is within 0.51 percentage points of the dense reference, and on C-KSA ($k_m=128$) 128K is 66.24 against dense's 66.31. This experiment cleanly removes the confound of "is the selection not good enough, or was the backbone damaged", and concludes that the former bottleneck can be solved by training while the latter need not be touched at all. It is the most convincing piece of argumentation in the paper.

5. It handles the "you trained more, so you are better" objection honestly.Table 11 runs continued pretraining of the unmodified Hybrid KSA, and the mean of all five checkpoints (5.7–51.3B tokens) is below the original checkpoint's 72.60. Rather than hiding a result unfavourable to its own recipe, the paper uses it to argue that the original checkpoint is a legitimate reference. Turning an adverse result into support for the argument deserves credit.

Limits

1. Evaluation stops at 128K.The longest long-context experiment is 128K, and one of the reasons given for $k_m = 128$ is precisely that "at 128K each layer holds only about 128 Meta entries, and compressing further saves little". The paper leaves higher compression ratios to "million-token contexts", but runs no million-scale experiment. The extrapolation range of "compressing harder is lossless at some lengths" has in fact never been tested.

2. At 4B only RULER is validated; neither general capability nor efficiency is measured.The conclusion says this directly: "General-capability evaluations and efficiency measurements are limited to 1.9B; the 4B validation covers RULER retrieval." That is, the paper has no answer to either "how much general capability does 4B lose" or "how much cache does 4B save and how much faster is it". And 4B is the scale closer to real deployment — all those impressive efficiency numbers in Section 18 (6.31 GiB, 44,971 tok/s) come from 1.9B.

3. Aggregation tasks such as FWE clearly degrade.RULER-128K frequent-word extraction falls from 45.00 to 26.67, a drop of 18.33 percentage points, close to half; VT also falls from 25.00 to 23.00. The paper flags the phenomenon in both the contributions section and the Failure mode discussion in Section 3.7, classifies it as "aggregation-heavy tasks such as frequent-word extraction degrade under block selection", and lists it alongside "the remaining cache is mainly original-text KV in the exact-access layers" as a principal cost. But the paper gives no mechanism-level explanation — why aggregation tasks degrade under block selection, and whether it can be mitigated. This is not a negligible corner: block-level sparsity inherently favours "a few high-weight positions", while aggregation tasks need information spread more diffusely, a structural tension between the two. The paper puts the RULER mean of 72.39 in a prominent place, but a reader must find Table 7 on their own to see the scale of this failure mode.

4. The remaining cost is concentrated in the sparse layers' original-text KV.The paper itself concedes in the conclusion that "The remaining cost lies mainly in the original-text KV stored by the sparse layers". There is a shadow of this in the numbers too: at 128K the index-key cache is only 3.86× smaller (KV cache) and 1.35× smaller (index-key cache), the latter showing that the index side does not disappear along with compression. C-KSA compresses the remote Summary, but the KV of selected original-text blocks must still be kept and read in full — a cost item that has not been touched.

5. The measurement basis for the efficiency data is narrow.It comes from 1.9B, BF16, batch size 1, a single H800. Batch=1 is the latency-oriented extreme, whereas real serving is usually throughput-oriented under continuous batching. The paper provides no data at large batch or under continuous batching.

Not disclosed, worth testing next

The following questions remain open after reading the paper. Each was checked against the paper first to confirm no answer is given, and is then phrased as an open question.

  1. The per-layer distribution of attention/information on Meta entries.The paper gives the qualitative observation of Figure 13: Meta entries take only 7.7–13.7% of attention mass in the shallow layers shown, but 73.1–87.8% in the middle and deep layers. That is, however, a visualization of one 16K NIAH sample and one query; the paper does not disclose cross-sample, cross-length per-layer statistics (such as per-layer curves of attention entropy or information content). An aggregate statistic would be worth producing, to establish whether "shallow layers use Meta less" is a reproducible general rule.
  2. Experiments with a different $k_m$ per layer.Section 3.1 explicitly says C-KSA supports layer-specific compression, but immediately states that every evaluated configuration uses a uniform $k_m$ across C-KSA layers, and puts "how to allocate compression across layers" into future work. Since item 1 above shows layers differ greatly in their reliance on Meta, it would be worth a set of experiments with heterogeneous per-layer $k_m$, to see whether better retrieval scores can be obtained at the same average compression rate.
  3. How the sparse decode kernel behaves at large batch / under continuous batching.The decode path the paper describes is "a custom sparse kernel reading the KV cache directly by selected block index", and the efficiency measurements are explicitly at batch size 1. Sparse access at batch=1 is almost purely memory-bandwidth bound; to be verified: as batch grows and different requests select different blocks, producing irregular memory access, does the kernel keep its relative advantage? This directly determines whether these speedups transfer to production serving.
  4. Efficiency numbers and general capability at 4B.The paper's conclusion already concedes that efficiency measurement and general-capability evaluation are limited to 1.9B, with 4B covering only RULER. Worth measuring: 4B's resident cache, prefill/decode throughput at 128K, and the nine general benchmarks — after all, 4B's added S-KSA parameters (163.0M) are nearly twice 1.9B's (86.6M), so its cost structure need not have the same shape.
  5. The effect of Indexer Q/K RMSNorm at 1.9B has not been reproduced.The paper reports that at 4B, without Q/K normalization, even 21.8B tokens of training stays below the C-KSA+Full parent, whereas with normalization 4.2B tokens are enough to recover to near the parent. But it states explicitly that 1.9B keeps the original setting and was not re-run through the full experimental suite with this change, and writes "whether normalization can similarly reduce the adaptation data needed at 1.9B" as an open question. This is the most concrete reproduction gap in the paper, and it bears directly on whether the "4.2B tokens is enough" figure transfers at 4B.

An overall assessment

If the report had to be summed up in one sentence: it does "converting an existing hybrid attention model" with unusual discipline — every modification has a single-factor control (the compression-path shape in Table 8, $k_m$ in Table 9(a), the sparsity scheme and teacher pooling in Table 9(b), the backbone choice in Table 9(c)), every key claim has reproducible numbers behind it, and the most challengeable point, "you trained more so you got better", is handled head-on by Table 11. The oracle experiment in Table 10 is the highlight: it first proves that "reading only 3.9% of positions retains 82.83% of attention mass", then proves that "if the selection is good, the backbone need not even change", thereby narrowing the problem precisely down to "how do we train a good Indexer".

Its boundaries are equally clear and must be acknowledged: evaluation stops at 128K, 4B covers retrieval only, the efficiency data is a single batch=1 measurement, and there is an obvious degradation on aggregation tasks that is recorded but unexplained (FWE 45.00 → 26.67). For a reader who wants to reproduce or adopt this scheme, the most valuable first step is probably to reproduce the oracle curve of Table 10 — it is the cheapest experiment that tells you whether your own backbone has the kind of attention concentration that makes sparsity viable; whether to go on to the full S-KSA adaptation then depends on whether your workload contains long-context tasks like FWE that require global aggregation.

One-line conclusion:at 1.9B, KSA V2 trades a 40.4% reduction in resident cache, 1.51× prefill and 1.23–1.32× decode for RULER essentially level with the parent model (72.39 vs 72.61); the trade pays off on retrieval-type tasks, is discounted on aggregation-type tasks, and has not yet been validated beyond 128K, at 4B efficiency, or under batching.
