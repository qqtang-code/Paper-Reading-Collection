01 · Overview

Overview: what this paper is arguing about

The conclusion first: this paper does not propose a new harness. It proposes a benchmark for evaluating harnesses. Its central claim is that long-context systems should be evaluated per model × harness pair, and that efficiency must be reported alongside accuracy.

The paper opens by naming two gaps. First, accuracy on existing long-context tasks has saturated: whether you use direct inference or wrap the model in an agentic harness, the scores bunch into a narrow band, so harness capabilities cannot be told apart. Second, accuracy alone hides cost: with the same underlying model, swapping the harness can change spend by an order of magnitude while accuracy barely moves — so the difference is invisible.

Figure 1 compresses both points. The upper panel places three benchmarks side by side: on LongBench-v2 and OOLONG-Synth the harness curves nearly coincide; only on the shaded LongHarness region (this paper) do they actually spread out. The lower panel switches to an accuracy-versus-cost scatter: on Outlier Memo Detection, RLM and mini-swe-agent land at similar accuracy, yet their costs differ by 12.4×.

02 · Background & Motivation

Background: what a harness is, and what older benchmarks miss

2.1 Defining "LM harness" first

The paper's definition: a harness is the control layer wrapped around a base model, responsible for managing its context, tools, and interaction sequence (Huang et al., 2026). For long-context reasoning, the harness lets the model work through an input far larger than its window over multiple turns, using the results of earlier steps to steer later ones.

The paper evaluates four harness families with different emphases. Understanding how each one reaches the context is the prerequisite for reading everything else:

  • OpenCode (Anomaly, 2026): a coding-agent harness that materialises context into files, so the model retrieves through shell and file operations and writes scripts to verify;
  • mini-swe-agent (Yang et al., 2024): the lightweight coding agent of the same family, with the same file and shell access but a leaner interaction loop;
  • RLM (Zhang et al., 2025): exposes the long prompt as a programmatically accessible object, splits it into smaller pieces via recursive sub-model calls, and lets the main model aggregate the results;
  • ReAct (Yao et al., 2023): interleaves reasoning and acting; here its action space is extended with semantic search, batched nearest-neighbour retrieval, and document reading, using BAAI/bge-m3 embeddings (Chen et al., 2024).

The tension is that these mechanisms can raise accuracy by spending more model calls and re-reading context, but the extra processing also raises cost. So judging their value requires measuring accuracy and compute spend together — that sentence is the paper's motivation.

2.2 Two structural gaps in older benchmarks

The paper classifies and critiques existing long-context benchmarks; the argument is worth restating in full:

  • LongBench v2 / HELMET (Bai et al., 2025; Yen et al., 2025): broad coverage, but tasks are mostly "recall a little relevant information plus a few reasoning steps". They test evidence retrieval, not situations where an intermediate conclusion repeatedly changes what should be retrieved next, so they probe a harness's adaptive retrieval policy only weakly.
  • LongProc (Ye et al., 2025): tests long procedural generation, but hands the model the detailed procedure and rewards faithful execution, which dilutes the strategy-selection component.
  • OOLONG-Synth (Bertsch et al., 2025): requires aggregation over a lot of information, but permits one universal divide-and-conquer strategy — classify each record independently, then aggregate. That route never has to revise retrieval in light of intermediate findings.

The conclusion: both directions impose substantial processing burden, but both lack coverage of the setting where hard retrieval and strategy choice jointly determine accuracy and cost. The authors therefore set their own design goal — tasks must couple diverse, adaptive retrieval with long-horizon reasoning, and must admit multiple solution routes with different costs.

Table 1 turns that argument into a checkable property matrix. Note the horizontal rule splitting it: the top five rows are task-level properties, the bottom two are system-level properties (whether a model–harness configuration is actually spread out on accuracy or cost). LongHarness is the only column with a ✓ in all seven rows.

Summary: this section converts "why build a new benchmark" into two testable propositions — (a) the tasks are strategy-sensitive (several solution routes with different costs), and (b) the systems are genuinely spread out (existing configurations show wide accuracy and cost distributions). Table 2 and Figures 3–4 are the evidence for (b).
03 · The Four Tasks

The four tasks: design intent in one figure

The paper first states five design criteria (mirroring the properties of Table 1): retrieval must be diverse and adaptive; the context must contain semantically confusable evidence that has to be verified; solutions must take multiple reasoning steps in which intermediate findings steer later retrieval; and tasks must admit several strategies with different costs, so that selective search and reuse of intermediate results become cheaper alternatives to brute force.

The four tasks are four concrete realisations of those five criteria. Figure 2 sets them side by side, and every panel follows the same three-part structure — Context → Query → Traces (with correct and incorrect solutions contrasted) — above a strip sketching the pool of documents, programs, or memos. It is worth walking through all four panels now; the per-task breakdown later will map straight onto them.

Laid out side by side, the retrieval character of the four tasks is plainly complementary:

That is precisely what "diverse retrieval strategies" in the title means.
04 · Task Deep Dive

Task-by-task breakdown: pitfalls and cheaper routes

4.1 Constraint Solving Search

Given a set of documents describing people, the agent must find every person who satisfies all conditions in the query simultaneously. Each instance holds about 120K tokens and about 160 people, with queries carrying 3–5 conditions (habits, current situations, relations to others). Exactly five people qualify, but their evidence is scattered across different documents and mixed in with "close but non-equivalent" counterexamples.

Go back to the top-left panel of Figure 2: Maya's night shift, commute habit, and fruit eating sit in three different passages, whereas Leo's "plans to take the bus next month" and "watermelon-scented candle" do not constitute the corresponding habits. The answer must name exactly those five IDs.

The paper plants a computable strategy gap here: during construction it deliberately requires one condition satisfied by ≤10% of people (the selective condition) and another by ≥60% (the prevalent condition), without telling the solver which is which. The efficient route therefore finds the condition with the fewest satisfying people, shrinks the candidate set, and then verifies the remaining conditions only on that set; the brute-force route checks all conditions against all 160 people, doing markedly more retrieval and reasoning. This is the first quantified instance of "same task, different cost".

Construction details (Appendix B.1, [organized]): start from a typed world containing 160 people and related entities, sample 3–5 predicates and build support sets so that exactly five people fall in the intersection of all of them; for each predicate, add 2–4 people who satisfy every other predicate but fail this one. Failing predicates are expressed by "close but invalid facts" (e.g. "plans to take the bus" rather than "has a commute habit") rather than by omission. Facts receive stable IDs and are grouped into passages of 2–5 statements, then padded with unrelated background facts; after keeping every passage that carries decisive evidence, neutral passages fill the context to 120K–128K tokens and everything is shuffled. A private solver performs the set intersection/union and maps it to passages; a verifier independently recomputes the world, confirms that each near match fails exactly one predicate, and checks the sizes of the selective and prevalent support sets plus the survival of the cited facts after packing.

4.2 Equivalent Program Pair Search

Given a set of programs, the agent must find every pair that produces the same output on the same legal inputs. Each instance holds about 100K tokens and 200 Python programs adapted from the APPS dataset (Hendrycks et al., 2021). Problem statements and visible input–output examples are removed, and each correct implementation is surrounded by mutants that look like they solve a similar problem but behave differently.

That yields a counter-intuitive consequence: the two genuinely matching programs may look less alike than a wrong candidate does. Ranking by code similarity is therefore unreliable — Appendix B.4 goes as far as requiring that every true pair rank behind at least 12 mutants by similarity.

The top-right panel of Figure 2 makes this concrete: cells 173 and 088 both test x >= target and are therefore equivalent; cell 026 drops the equals sign to x > target, which behaves differently — feed it an input containing the target itself and the two diverge immediately. The efficient route is consequently two-stage: infer each program's purpose and group plausible matches, then use distinguishing inputs to eliminate behavioural variants within a group.

The answer must list the complete set of matching ID pairs, and the number of pairs is not disclosed. The paper is also candid about the label's scope: the answer key treats "both programs pass the original problem's tests" as a match, which is not a proof of equivalence over all possible inputs.

4.3 Program Execution Tracing

This task asks the agent to reconstruct the result of an eight-step query program from 320 shuffled records of earlier Python computations. Each cell records its own ID, its function, an example call, and the output.

For each step of the query, the agent must find the cell whose function is semantically equivalent and whose recorded call used the required input. Because the previous step's output is the next step's input, retrieval is step-dependent: the exact numeric input narrows the search by literal matching, but the deliberately confusable functions may return the same output on the displayed example and differ on other inputs.

The bottom-left panel of Figure 2 contrasts correct and incorrect paths: the correct path uses cell 89's output 2 as a key to find cell 17, giving the result [2, 3]; the incorrect path takes cell 52 (whose output also happens to be 3, but whose function is something else), so the key becomes 3, the next retrieval is steered to cell 104, and the final result comes out wrong as [2, 3, 4]. The caption Wrong downstream answer! is there to stress that a single mismatched cell rewrites every later search key.

The answer comprises the eight selected cell IDs plus the exact final result (JSON). The efficient route uses each recovered output as the next search key, verifies the function match, and directly reuses the recorded result, thereby avoiding recomputation of work already present in the context — but that demands rigorous state tracking and step-by-step semantic verification.

Construction details (Appendix B.3, [organized]): sample an eight-node computation graph, assign each node a typed transformation drawn from ten families (table and set operations, sequences and text, intervals, grids, paths, graph traversal, topological batching, and so on), and execute the graph to obtain each node's input and output. Build 20 cells per node: exactly one implements the transformation over its full input contract, while the other 19 are controlled perturbations of boundary handling, filtering, aggregation, or sorting — and a perturbation is kept only if it yields the same output on the displayed call yet differs on another contract probe. A second 20-cell pool is then built around the alternative input the solver would reach after an earlier mistake. The 8 × 40 = 320 cells are anonymised and shuffled, and the public context never marks which pool a cell came from.

4.4 Outlier Memo Detection

The agent must find memos whose statements contradict a relation established elsewhere in the collection. Each instance contains 700 labelled memos and 2,500 statements about people, organisations, objects, and their relations. Exactly 15 memos carry a conflicting statement, and no contradiction is visible in isolation.

Bottom-right panel of Figure 2: one memo says Ms. Lee teaches Algebra 101, another schedules her class for Monday at 9:00 a.m.; only together do they conflict with a third statement placing the course's instructor on Friday at 2:00 p.m. Because there is heavy paraphrase and plenty of "related but consistent" material, topic similarity is not a sufficient criterion. The answer must name exactly those 15 memo IDs.

The paper frames the strategy gap as "build one global structure" versus "repeat local retrieval": the efficient route reads the packet once, organises statements into a reusable relation table or graph, and then checks each derived claim by composing fact pairs; the inefficient route hunts for evidence separately for every suspect claim, which both re-reads the same memos and misses contradictions that only surface when several memos are combined.

Construction details (Appendix B.2, [organized]): built from a typed relation graph. Two-hop rules compose edges \(R_1(a,b)\) and \(R_2(b,c)\) into the derived claim \(R_2 \circ R_1(a,c)\). The generator samples 450 base edges, computes 440 derived claims, then picks 15 and replaces the correct endpoint \(c\) with another entity \(c'\) of the same type. Because the two base edges that establish the correct endpoint remain in the packet, every corruption comes with a complete symbolic contradiction proof. Near-twin decoys reuse the same relation types, and a wrong endpoint may even be "correct" for another anchor or relation, which blocks shortcuts along entity names. The final packet holds 700 memos and exactly 2,500 atomic statements drawn from five business domains.
Summary ([organized]): viewed together, the authors' strategy is to give each retrieval form its own task, and to build into every task an identifiable but unlabelled cheaper route — selective conditions, grouping and pruning, reuse of intermediate outputs, and building a global relational structure. Efficiency is thus not a metric bolted on afterwards but a degree of freedom endogenous to the task design.
05 · Main Results

Main results: a 68% ceiling and a 12.4× cost gap

5.1 Experimental setup

Models and harnesses. The evaluation covers five models: GPT-5.6-sol, Gemini 3.8 Flash, Qwen3.8-27B, GLM-5.3, and Kimi-K2.6 (OpenAI, 2026; Zeng et al., 2026; Qwen Team, 2026; Moonshot AI, 2026). Each model runs five configurations: direct long-context inference (Direct) as the baseline, plus four agentic harnesses — RLM, OpenCode, mini-swe-agent, and ReAct (Yao et al., 2023). On reasoning effort, GPT-5.6-sol / Gemini 3.8 Flash / GLM-5.3 use high, Qwen3.8-27B uses medium, and Kimi-K2.6 uses its reasoning-enabled mode.

Evaluation protocol. Each instance gets a 3M-token budget, counted as cumulative input + output across all model calls. Accuracy reported is task-specific strict exact match: Program Execution Tracing requires both the final result and the cited cells to be exact; Outlier Memo Detection requires the set of 15 memo IDs to be exact; Constraint Solving Search requires the person-ID set to be exact; Equivalent Program Pair Search requires the set of five unordered pairs to be exact.

Cost accounting: the cost the paper reports is an estimated per-instance cost obtained by converting recorded token usage through API rates (rate card in Table 6); rates are applied to each API call before averaging across instances. For the self-hosted Qwen runs the paper reports an "equivalent API cost". Appendix A (Table 4 in Section 8 of this page) gives mean input/output token counts.

5.2 The benchmark is still hard

Table 2 is the paper's centrepiece: 5 models × 5 configurations = 25 rows, each cell reporting accuracy (%) followed by USD cost per instance, with a final macro-average column (the arithmetic mean of the four task accuracies plus the mean of the per-task average costs).

Three points the paper stresses repeatedly follow directly from this table:

  • It is hard. The best configuration, GPT-5.6-sol × mini-swe-agent, reaches only 68.0%; the strongest non-GPT configuration (GLM-5.3 × mini-swe-agent) reaches 42.5%; Kimi-K2.6 never exceeds 1.5%.
  • Difficulty varies by task. Per-task best scores fall from 100% on Outlier Memo Detection all the way to 52% on Equivalent Program Pair Search.
  • No configuration wins everywhere. Not one configuration leads on all four tasks at once.

5.3 Similar accuracy can come with very different cost

The paper offers a very clean contrast: on Program Execution Tracing, GPT-5.6-sol direct inference and OpenCode score 94% and 96% — apparently a tie; but the former uses 0.121M input tokens for $0.648 while the latter uses 1.29M input tokens for $1.37, roughly 10.7× the input and about 2.1× the cost ([estimated]: 1.29 ÷ 0.121 from Table 4). The same holds on Constraint Solving Search: direct inference 58% @ $0.690 versus OpenCode 56% @ $1.72 — two points lower accuracy at 2.5× the cost.

Figure 3 plots the 25 combinations of Table 2 on a plane of macro accuracy versus mean cost per instance (log axis). How to read it: colour is the model, shape is the harness, and each model's highest-accuracy configuration carries a callout. Its value is turning "which one should I pick?" into a visual judgement that needs no absolute threshold — the top-right is accurate-but-expensive, the top-left is accurate-and-cheap, and the top-left is almost exclusively occupied by GPT-5.6-sol.

The paper adds two sharper counter-intuitive contrasts showing that more inference is neither necessary nor sufficient:

  • On Pairs: GPT-5.6-sol with RLM scores just 2% at $7.86, whereas direct inference is 44% @ $0.780 and ReAct is 52% @ $2.68. Spending nearly ten times as much drops accuracy to 1/22 of the direct baseline.
  • On Memos: RLM reaches 92% at $7.23; mini-swe-agent reaches 100% at $0.583. The latter spends less than a twelfth as much and still gains 8 points.

5.4 Weaker models gain more from harnesses

The paper observes a systematic pattern: the gain a model obtains from its best harness is inversely related to its direct-inference accuracy — the worse direct inference is, the more the harness helps.

Summary: three sentences at the results layer — (a) the ceiling is only 68%, so the tasks are far from solved; (b) at equal accuracy, cost can differ by an order of magnitude, so accuracy-only evaluation is informationally incomplete; (c) the harness acts as a compensator for the model, and weaker models benefit more, which makes conclusions drawn from model names alone misleading.
06 · Harness Mechanisms

Mechanism attribution: why each harness wins or loses

The main table says who wins and who loses; this section says why. The paper's unifying lens is: a harness spends extra model calls to reduce the amount of context that must be handled at each step; the payoff depends on how much those calls actually simplify the remaining work.

6.1 How to read the change plots: Figure 4

Figure 4 is the second densest figure in the paper: a 2 × 3 grid of six panels, with Constraint Solving Search, Equivalent Program Pair Search, and OOLONG-Synth on the top row, and Program Execution Tracing, Outlier Memo Detection, and LongBench-v2 on the bottom row. In every panel the x-axis is the cost multiple relative to direct inference (log scale ½× / 1× / 4× / 16×) and the y-axis is the accuracy change relative to direct inference, in points.

The key to reading it is the background shading: the intersection of the 1× line and the 0 line is the direct-inference reference point; the green region means more accurate and cheaper, the pink region means worse and more expensive. A point moving toward the upper left is good; toward the lower right, bad.

6.2 File-and-shell harnesses: OpenCode and mini-swe-agent

File and shell access supports both targeted retrieval and scripted verification, and those two pay off very differently. The paper gives one example in each direction:

  • On Program Execution Tracing, targeted retrieval buys little. OpenCode's approach is to take each step's recorded output, search for the cell that uses that value as input, and verify which one implements the next query step. For GPT-5.6-sol this moves accuracy from 94% to 96% — a small gain against an already strong direct baseline, while cost rises from $0.648 to $1.37.
  • On Outlier Memo Detection, scripted verification raises accuracy and cuts cost at once. mini-swe-agent collects facts into a table and then uses local scripts to compose and check claims, reducing how often the model re-reads. With the same model it reaches 100% @ $0.583, versus 44% @ $1.17 for direct inference — both more accurate and cheaper. OpenCode, by contrast, tends to re-read the packet or to audit overlapping memos with separate model calls, reaching only 10% @ $3.11.

The paper's generalisation: targeted retrieval produced only a small accuracy gain on execution tracing, whereas scripted verification improved both accuracy and cost on memo detection — the difference being that the latter sediments intermediate results into a reusable artefact.

6.3 Programmatic decomposition: RLM

RLM's mechanism is to filter the long prompt into smaller fragments, process them through additional sub-model calls, and let the main model aggregate the outcomes (Zhang et al., 2025).

  • On Memos it works, but expensively: it recovers 92% of the outliers at $7.23, whereas mini-swe-agent reaches 100% @ $0.583 with a local program inspecting the packet.
  • On Pairs it fails characteristically: RLM uses sub-calls to infer each program's purpose and form broad problem families. That is useful as a first filter, but this benchmark packs each family with many behaviourally different mutants, so an efficient solution must prune with distinguishing inputs before verifying. RLM spends most of its recursion on the initial grouping, and too many candidates remain when it reaches the final comparison — 2% @ $7.86 against 44% @ $0.780 for direct inference.

The paper's diagnosis is strikingly compact: decomposition reduced the context per call but did not sufficiently shrink the final decision space. That sentence is essentially the core argument for why long-context harnesses cannot rely on chunking alone.

6.4 Vector retrieval: ReAct

The paper offers a criterion: semantic retrieval is most useful when the retrieved item is itself a credible comparison candidate.

  • It holds on Pairs. Using one program as a query surfaces implementations that look stylistically different but plainly share a purpose, turning a search over 200 programs into a much smaller neighbourhood. The model still has to reject neighbouring mutants, but this candidate list lifts GPT-5.6-sol from 44% @ $0.780 to 52% @ $2.68.
  • It does not hold on Memos. That task cannot be solved by judging each memo in isolation — a wrong memo is only exposed by combining the facts of two other memos. Similarity search tends to return memos that are "related but insufficient to complete the evidence chain" and never checks each claim. ReAct therefore reaches only 6% @ $2.77, below the 44% @ $1.17 of direct inference.

The way the paper closes this section is worth copying: the value of extra inference depends on how it organises the work that follows. Targeted search, a reusable fact table, and a smaller candidate set can all support efficient verification; repeated reading and broad candidate lists only add cost while leaving the core reasoning undecided.

Summary ([organized]): the four mechanisms line up along one question — what did each do to the decision space? mini-swe-agent compressed the decision space into a script on Memos, hence accurate and cheap; ReAct compressed the candidate neighbourhood on Pairs, hence a small win; OpenCode compressed very little on execution tracing, hence 2 points for double the cost; RLM compressed per-call context but enlarged the final decision space on Pairs, hence a heavy loss. That criterion is far more actionable than "is this harness good?".
07 · Comparison

Head-to-head: why the old benchmarks cannot separate harnesses

To show that "the new suite is more discriminative" is not a self-serving claim, the paper runs subsets of two existing benchmarks on the same backbone (GPT-5.6-sol): 50 examples from the 128K condition of OOLONG-Synth (Bertsch et al., 2025), and 50 examples from LongBench-v2 in the 90K–128K token range (Bai et al., 2025).

The subsets are constructed as follows (Appendix B.5, [organized]): for OOLONG-Synth, two disjoint 25-example queues are drawn with a fixed random seed from the 400 test examples of the official context_len=131,072 condition and spread as evenly as possible across the counting / timeline / user task groups, yielding 17 counting, 16 timeline, and 17 user examples, with each queue covering all eight source datasets and all 16 context-window IDs; for LongBench-v2, the full zero-shot prompt is tokenised with the Qwen3.8-27B tokenizer and the 75 examples in the 90K–128K token band are kept (42 hard + 33 easy), with all hard examples retained plus eight deterministically chosen easy ones, giving 50 examples that cover all six eligible domains and 13 eligible subdomains, with answer positions A–D counted at 12/12/13/13 and prompt lengths from 90,049 to 127,548 tokens (mean 108,808). The paper states explicitly that this is a hard-weighted, length-controlled subset and is not intended to reproduce the full benchmark's distribution.

The result is the story told jointly by Table 3 and the right-hand column of Figure 4: on OOLONG-Synth, every tested agentic harness beats direct inference, with accuracy rising from 64% to between 70% and 86%; on LongBench-v2, all five configurations bunch into a narrow 60%–68% band. In other words, these benchmarks either say "uniformly positive" or barely distinguish harnesses at all.

The paper lands this section on cost: under the same 128K-class context budget, mini-swe-agent scores 68% @ $0.816 on this suite, the same 68% for only $0.190 on LongBench-v2, and 86% @ $0.217 on OOLONG-Synth. It also makes a strict accounting disclaimer — "exact success" means different things across the three benchmarks, so these percentages cannot be treated as normalised difficulty measures. But even comparing only within a benchmark, the lower ceiling and higher cost on this suite show there is ample room left for future harnesses on both the effectiveness and the efficiency side.

Summary: this section is the linchpin experiment — it turns "our benchmark is more discriminative" from a design claim into a direct contrast with two external benchmarks: the accuracy–cost region those benchmarks cover is a single one, while the four tasks here cover all four classes (better-and-cheaper / better-and-pricier / worse-and-cheaper / worse-and-pricier).
08 · Appendix

Construction method and cost accounting (Appendices A/B/C)

8.1 The unified construction principle

Appendix B opens with the five-step construction pipeline shared by all four tasks; it is the key to why this benchmark's answers are deterministic:

  • ① Build the underlying structured data first — a predicate support set for constraint solving, a typed relation graph for outlier detection, a computation graph for execution tracing, an executable program family for equivalence pairing. These hidden records fix the answer before the public context is ever written.
  • ② Derive the gold answer and its supporting evidence with a task-specific solver or execution engine.
  • ③ Manufacture hard distractors through controlled modifications of the records.
  • ④ Render every item into its public form and shuffle.
  • ⑤ Recompute the answer from the same records with deterministic rule-based checks, verifying that each required item and each distractor plays its intended role.

Table 5 lists, per task, the trio of "private specification / controlled distractors / how gold is derived". It earns a look of its own because it shows that the public context exposes only the rendered items, never their role or provenance — a solver cannot tell from the format which item is a SUPPORT and which is a DISTRACTOR.

8.2 The detailed token and cost ledger

Table 4 is Appendix A: it gives, for all 25 configurations on the four tasks, accuracy (a) and mean input/output token counts with cost (b). It is the expanded form of Table 2 — Table 2 reports only cost, while Table 4 splits cost into input and output, which makes "where does the cost difference come from?" answerable.

8.3 API rates: how the dollar figures are produced

Table 6 lists the rates used to convert recorded token usage into the costs the paper reports. The paper notes specifically that rates are applied to each API call before averaging across instances, and that GPT-5.6-sol's long-context tier takes effect when a single request exceeds 272K input tokens.

One easily missed accounting detail: in the note to Table 4 the paper states that the Program Execution Tracing column uses a format-tolerant answer-and-citation rescore, with the original strict-format scores retained in the task reports. In other words, that column has already been through one round of format leniency — a reminder not to read Table 4's Program column interchangeably with the strict accounting of the other three tasks.
Summary: the three appendix sections each settle one reproducibility question: B answers "how is the data guaranteed to have a single determinate answer", A answers "does the cost difference come from input or output", and C answers "at what price list were the dollar figures converted". Stacked together, every accuracy and dollar figure in the paper traces back to a constructed record or a rate card.

10 · Commentary

Commentary: contributions, limits, and what is worth measuring next

10.1 What this paper gets right

  • It promotes efficiency from a side metric to a first-class evaluation axis. The core evidence (the 12.4× cost gap, and 94% versus 96% at 10.7× the input tokens) shows that in long-context settings an accuracy-only evaluation systematically conceals the gap between harnesses. The point is validated across four tasks and 25 configurations in Section 4, not by a single anecdote.
  • The tasks are strategy-sensitive rather than strategy-agnostic. Every task embeds an identifiable but unlabelled cheaper route (selective conditions, grouping and pruning, reuse of intermediate outputs, building a global relational structure). That makes efficiency an endogenous degree of freedom of the task design rather than a metric added afterwards — a technically harder achievement than simply making contexts longer.
  • Answer determinism comes from construction, not from human annotation. Appendix B's pipeline — private structured data → generate gold → controlled distractors → render and shuffle → rule-based verification — fixes gold before the public context is written, and allows the answer to be recomputed by rules. That makes the evaluation reproducible and the role of each distractor verifiable.
  • The hard distractors are targeted rather than random noise. This is the most fundamental difference from long-context benchmarks that merely stuff irrelevant text: failing predicates are expressed as "close but invalid facts"; mutants must match on the displayed call yet differ on a contract probe; true pairs are required to rank behind at least 12 mutants by similarity; and a wrong endpoint may be correct for another anchor. Those constraints kill the shortcut through surface similarity.

10.3 Limitations the paper states itself

The paper proactively declares the boundaries of its answer keys in two places, and both are worth remembering verbatim:

  • The equivalence-pair labels are "operational equivalence". The answer key treats "both programs pass the original problem's tests" as a match, and the paper states explicitly that this does not constitute a proof of equivalence over all possible inputs; similarly, execution-tracing verification is behaviour verification against explicit input contracts, not a proof of equivalence over arbitrary Python objects.
  • Cross-benchmark percentages cannot be normalised into difficulty. Section 4.5 states clearly that the three benchmarks define "exact success" differently, so figures like 68% / 68% / 86% are not task-normalised difficulty measures and support only within-benchmark comparison. It also notes that the LongBench-v2 subset is hard-weighted and length-controlled and is not intended to reproduce the full benchmark's distribution.

10.4 Not disclosed, worth testing next

  • Variance and distribution of per-instance cost. The paper reports mean cost per instance and mean input/output tokens; no standard deviation, percentile, or share of over-budget instances was found in this reading. Under a 3M-token budget, an average of $7.86 could be driven by a few instances that blow the budget, or could be broadly expensive — and those two pictures imply very different harness-selection advice. Worth measuring: the cost distribution and the budget-exhaustion rate.
  • Instance counts and statistical uncertainty. The main text and appendices give the construction of the subsets (e.g. 50 OOLONG examples, 50 LongBench-v2 examples), but this page did not find disclosed instance counts for the four LongHarness tasks themselves, nor confidence intervals or run-to-run variance. On cells near saturation (100% and 92%) and near the floor (0% and 1.5%), the instance count directly determines the strength of the conclusion. Worth measuring: N per task, variance across repeated runs, and whether accuracy differences are significant.
  • Sensitivity of cost to harness interaction limits. Table 4 shows cost is driven mainly by input tokens (e.g. OpenCode uses 1.2M–2.8M input tokens on several tasks), but the paper does not disclose whether maximum turn/step limits, retry policies, and truncation policies are held constant across harnesses. If harnesses have different "patience budgets", part of the cost gap is configuration rather than mechanism. Worth measuring: cost–accuracy curves under a fixed interaction limit.
  • Effect of README and prompt wording on results. The paper does not report prompt templates, tool-description wording, or whether any per-task instruction tuning was applied — yet a swing like mini-swe-agent's from 100% on one task to 42% on another in Table 2 is plausibly sensitive to instruction wording. Worth measuring: robustness under instruction perturbation.
  • Asymmetric harness coverage against existing benchmarks. The comparison in Table 3 uses a single backbone, GPT-5.6-sol (the paper states the external benchmarks use GPT-5.6-sol), whereas this suite covers five models. So the claim "old benchmarks cannot separate harnesses" has so far been verified only within one model family; whether they saturate equally for weak models is not disclosed. Worth measuring: rerunning those two comparison benchmarks across multiple backbones.
Overall assessment: this is an evaluation-methodology paper. Its contribution is not a new algorithm but a redesign of the evaluation accounting — construction guarantees determinate answers, controlled distractors guarantee hard retrieval, built-in multiple strategies make efficiency measurable, and a cost column makes efficiency readable. Its strongest evidence is not "the best is only 68%" (that only shows the tasks are hard) but the 12.4× cost gap on the same model and task, and counterexamples like "RLM 2% @ $7.86 versus Direct 44% @ $0.780" — which directly falsify the implicit assumption that more inference means better. For anyone doing inference serving or agent engineering, the most practical takeaway is the contrast in Section 6.2: within agentic harnesses, sedimenting intermediate results into a reusable scripted artefact (mini-swe-agent on Memos) versus repeatedly re-reading the context (OpenCode on the same task) yields one configuration that is both accurate and cheap and another that is neither.
